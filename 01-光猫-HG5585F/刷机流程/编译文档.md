## 2. 配置层（顺序不能换）

`scripts/hg5585f/gen-config.sh` 用 `scripts/kconfig.pl` 按顺序合并，**后者覆盖前者，包括 `# ... is not set`**：

```
configs/an7581.config           上游完整基线
configs/release.config          上游 11 行额外包（含 luci-app-upnp=y）
configs/hg5585f-profile.config  12 个 device -> CU/CT 两个
configs/hg5585f-build.config    最后一层：ccache/能力锚点/去 UPnP/去 EN7572/zram
```

规则：

1. **要关一个包，必须写在 `hg5585f-build.config`（最后一层）**，写在前面会被 `release.config` 覆盖。
2. `release.config` 里的 `CONFIG_PACKAGE_luci-app-upnp=y` 还在；靠最后一层关掉，**不要删这层**。
3. 改完先干跑，不要直接烧 CI：

```sh
python scripts/hg5585f/kmerge.py configs/an7581.config configs/release.config \
    configs/hg5585f-profile.config configs/hg5585f-build.config > /tmp/c.cfg
python scripts/hg5585f/kmerge.py --check /tmp/c.cfg
```

4. `gen-config.sh` 在 `make defconfig` 之后会跑 `assert-config.sh`，约 30 秒失败，避免烧 3 小时。断言检查：
   - device 恰好 2 个（CU/CT）；
   - firewall4 / dnsmasq-full / ppp / PPPoE / nft offload 全在；
   - `kmod-nf-conntrack-bridge`、`kmod-nf-flow`、`kmod-nft-bridge`、`kmod-nft-offload` 在；
   - `br_netfilter` **不在**；
   - `luci-app-upnp` / `miniupnpd-nftables` **不在**；
   - PON 栈（xpon / paged-bosa / ponctl / pond / luci-app-pon）在；
   - `kmod-airoha-en7572` **不在**；
   - `zram-swap` 在；
   - initramfs/squashfs/ccache 在。

## 3. GitHub Actions 构建

### 3.1 手动触发

```sh
gh workflow run build-hg5585f \
  --repo Bernardxu123/ponwrt-hg5585f \
  --ref master \
  -f proxy=passwall \
  -f build_recovery=true \
  -f make_release=true \
  -f release_tag=v2026.10.18-2
```

- `proxy` 三选一：`passwall`（默认，小内存首选）/ `openclash`（Clash 订阅原生，但要编 Ruby）/ `none`（只验证链路）。
- `build_recovery=true` 多产一个 `recovery.itb`，约多 10–16 分钟；撞 350 分钟上限时改 `false`。
- `make_release` 现在**默认 true**：编完直接进 Releases。
- `release_tag` 留空时：tag 触发用 ref 名，手动触发用 `v<日期>-<短SHA>`。

### 3.2 看运行与失败日志

```sh
gh run list --repo Bernardxu123/ponwrt-hg5585f --limit 5
gh run watch <run-id> --repo Bernardxu123/ponwrt-hg5585f
gh run view <run-id> --repo Bernardxu123/ponwrt-hg5585f --log-failed
```

构建步骤顺序：

```
清理磁盘 → /mnt 大盘 → 装依赖 → 恢复 dl/ccache → feeds → overlay 检查
→ 生成 .config（含断言）→ 算工具链 key → 恢复工具链（cache→Release 备份）
→ 下载工具链源码 → 处理工具链（miss 才编）→ ccache 兜底
→ 保存工具链（cache + Release）→ make download（3 次重试）
→ 编译（按内存动态 -j）→ 保存 dl/ccache（失败也保存）→ 产物校验 → 上传 → Release
```

### 3.3 打 tag 出正式包

```sh
git tag v2026.10.19
git push origin v2026.10.19
```

tag 触发会编译并自动创建 GitHub Release（prerelease）并上传。

⚠️ **如果手上已经有一份验证过的 artifact，不要为了发 Release 去 push tag**——那等于白烧一轮。
直接把现有 artifact 发布即可：

```sh
gh run download <run-id> -R Bernardxu123/ponwrt-hg5585f -n <artifact-name> -D /tmp/fw
gh release create v2026.10.18 /tmp/fw/* \
  --repo Bernardxu123/ponwrt-hg5585f \
  --target "$(git rev-parse HEAD)" \
  --title "HG5585F v2026.10.18" --notes-file /tmp/notes.md --prerelease
```

注意 `--target` 必须给**完整 40 位 SHA**，短 SHA 会报 `Release.target_commitish is invalid`。
另外，用 Releases API 建 tag 同样会触发一次 tag 构建，建完记得 `gh run cancel <id>`。

已发布：`v2026.10.18`（Passwall，commit `5b12fdb`），8 个资产，本地副本在
`光猫-HG5585F/downloads/ponwrt-v2026.10.18/`（sha256 已复核）。

### 3.4 缓存（2026-10-18 重构）

实测基线：**编译 3h02m49s / 总 3h13m = 94%**，其余 20 步只有 11 分钟。
所以只优化工具链，别的都是无效功。

| 缓存 | 内容 | key | 说明 |
|---|---|---|---|
| **工具链**（主力） | `staging_dir/host*` + `staging_dir/tool*` | `ponwrt-toolchain-airoha-an7581-<md5(tools/ + toolchain/ 的 Makefile) 前16位>` | 源码不动就一直命中；上游改工具链自动重建 |
| 工具链备份 | 同上，打包成 `.tzst` | 同上 | Release 资产（tag `toolchain-cache`），绕开 10 GB 配额，**不会过期** |
| dl | `make download` 的源码包 | `dl-<年+周>` | 用周号而非 run_id，避免每次存新副本挤掉旧缓存 |
| ccache | `$SRC/.ccache` | `cc-<年+周>` | 必须带 `CCACHE_DIR=$SRC/.ccache`（`rules.mk` 用 `CONFIG_CCACHE_DIR`） |

三条硬规则：

1. **`make tools/download toolchain/download` 必须在编工具链之前**——`make toolchain/install`
   不会自动补下载，只会解压 `dl/` 里已有的包，报错是 `Can't open dl/musl-*.tar.gz`。
2. **ccache 与工具链缓存会打架**：`tools/Makefile` 里 `ifneq ($(CONFIG_CCACHE)$(CONFIG_SDK),)`
   才编 `tools/ccache`。若缓存是「未开 ccache」时建立的，命中后跳过 `make tools/install`，
   `staging_dir/host/bin/ccache` 不存在，而 `rules.mk` 的 `TARGET_CC := ccache ...` 仍会调它
   → `Error 127`，整个构建失败。CI 里已加兜底：缺二进制就 `make tools/ccache/install`，
   再失败就 `sed` 关掉 `CONFIG_CCACHE` 继续编。
3. **不缓存** `build_dir` / `bin`：压缩后 8–12 GB，解压比重编还慢。

另有两个辅助机制：

- **`keep-cache-alive.yml`**：每 5 天 `lookup-only` touch 一次缓存（7 天不访问会被回收）。
  工具链能精确命中；dl/cc 含周号只能 best-effort。全部失效也不会出错，只是慢一点。
- **失败也保存**：`actions/cache/restore` + `actions/cache/save` 显式分离，save 步骤 `if: always()`。
  `actions/cache` 自带的 Post 保存在 job 失败时是 **skipped**。

### 3.5 并发数

按可用内存动态算，不写死 `nproc+1`：

```sh
JOBS=$(awk -v p="$(nproc)" '/^MemAvailable:/{m=int($2/2097152)+1} END{print (m<p?m:p)}' /proc/meminfo)
```

每个 `cc1` 约 1.5–2 GB RSS，4 核 16 G 上 `-j8` 容易被 OOM killer 杀掉，
而 OOM 的报错只是一句 `Killed`，很难看出是并发太高。

## 5. 已知构建失败与处理

| 现象 | 原因 | 处理 |
|---|---|---|
| `package/feeds/packages/miniupnpd` 失败，`020-descr-filter-fix.patch` 5/7 hunks FAILED | feed 把 miniupnpd 升到 2.3.11，补丁没同步；`release.config` 又开着 `luci-app-upnp=y` | 最后一层显式 `# CONFIG_PACKAGE_luci-app-upnp is not set` + `miniupnpd*` not set；断言已加。**不要重新开 UPnP** |
| 其他 feed 包 patch 打不上 | ImmortalWrt feed HEAD 漂移 | 优先在最后一层关掉该包；必须保留就 pin `feeds.conf.default` 到已知 commit，**不要改 feed 里的补丁** |
| `CONFIG_PACKAGE_kmod-airoha-en7572=m` 又出现 | 基线 `an7581.config` 自带 `=m` | `hg5585f-build.config` 里 `# ... is not set`；HG5585F 用 paged BOSA，EN7572 是多余前端 |
| 编译到 350 分钟超时 | Rust `rust/host`（airoha-ponctl/airoha-pond）现编，ccache 不覆盖；冷构建接近上限 | 先用 `build_recovery=false` 省 10–16 分钟；或打 tag 前先跑一次 `toolchain-only` 预热；不要缓存 build_dir |
| 磁盘不足 | runner `/` 只有 20–29 GB | 保留工作流的清理、`/mnt` 切换、28 GB 硬闸门；不要删 |
| `make download` 失败 | 某个源码包 404/网络抖动 | 看 `gh run view --log-failed`；dl 缓存失败也会保存，重跑通常能续 |
| **Go 包失败**：`geoview` / `hysteria` / `xray-core` 报 `no required module provides package X/internal/Y`、`build constraints exclude all Go files` | **`dl/go-mod-cache` 里的模块元数据被删了**。2026-10-18 踩过：抄参考仓库的 `find dl -size -1024c -type f -delete` 没加 `-maxdepth 1`，递归删掉了 `dl/go-mod-cache/cache/download/**/@v/` 下 **1131 个** `.mod`/`.info`/`.ziphash`/`list`。`.mod` 没了 → Go 算不出完整模块图 → 那些 `internal/*` 子包"不属于任何模块" | 清理命令必须 `find dl -maxdepth 1 -size -1024c -type f -delete`。**修完还要删掉被污染的 `dl-<周号>` 缓存**，否则下次又复原 |
| 编译失败但 `make -j1 V=s` 也没报清 | 并行日志交错 | 下载 `build.log` 与 `logs/`，搜第一个 `Error`/`FAILED` |

**不要做的事**：

- 不要开 `luci-app-upnp` / `miniupnpd`。
- 不要装 `kmod-br-netfilter`。
- 不要重新 pin `kmod-airoha-en7572`。
- 不要在 512 MB 的 ONT 上同时装 OpenClash + Passwall。
- 不要把 PPPoE 账号、LOID、设备 MAC 写进公开仓库。

1. `profiles.json` 里**恰好** `fiberhome_hg5585f-ct` / `fiberhome_hg5585f-cu` 两个 device；
2. 每个 device 必须有 `sysupgrade` 镜像；

## 7. 分流包（编译时三选一）

**ImmortalWrt feeds 自带 Passwall 和 OpenClash，不需要额外 feed**；只有 nikki 要加 feed。这是参考仓 `qwpianzhang/Actions-OpenWrt-HG5585F` 验证过的。

分流不再是"下一版"，而是 workflow 的 `proxy` 输入，默认 `passwall`：

| proxy | 配置文件 | 适合 | 代价 |
|---|---|---|---|
| `passwall`（默认） | `configs/hg5585f-proxy-passwall.config` | 512 MB 首选；Xray/SingBox/Hysteria | Clash 订阅需要转换；不装 Shadowsocks-Rust（会拉 Rust）；约 +30~40 分钟 |
| `openclash` | `configs/hg5585f-proxy-openclash.config` | Clash 订阅/规则原生 | DEPENDS 有 `+ruby +ruby-yaml`，Ruby 源码编译约 +15~25 分钟；运行内存更高 |
| `none` | 无 | 只验证 PON/PPPoE/路由 | 不含任何代理 |

两者互斥，`assert-config.sh` 会检查。Passwall 的具体组合（`configs/hg5585f-proxy-passwall.config`）：

```
CONFIG_PACKAGE_luci-app-passwall=y
CONFIG_PACKAGE_luci-app-passwall_INCLUDE_Xray=y
CONFIG_PACKAGE_luci-app-passwall_INCLUDE_SingBox=y
CONFIG_PACKAGE_luci-app-passwall_INCLUDE_Hysteria=y
CONFIG_PACKAGE_luci-app-passwall_INCLUDE_Simple_Obfs=y
CONFIG_PACKAGE_luci-app-passwall_INCLUDE_V2ray_Geoview=y
CONFIG_PACKAGE_luci-app-passwall_INCLUDE_V2ray_Plugin=y
# 不装 Shadowsocks_Rust_Client / Server，避免 Rust 工具链
```

nikki（mihomo）本仓库**没做**——它需要额外 feed（`src-git nikki https://github.com/nikkinikki-org/OpenWrt-nikki.git;main`）。想要更轻的 Clash 方案，加 feed 后照 `openclash` 那个文件的写法再加一个层即可。

**flow offload 与 tproxy 冲突已自动处理**：`99-hg5585f-setup` 检测到分流内核存在时，
自动设 `flow_offloading=1` + `flow_offloading_hw=0`（只保留软件 flowtable，
避免硬件卸载把被代理的流甩给 PPE 绕开 tproxy）；没有分流内核时两者都开。
实测代理流量仍有异常就全关：

```sh
uci set firewall.@defaults[0].flow_offloading='0'
uci commit firewall && /etc/init.d/firewall restart
```

## 8. 刷机前置（详见 flash-SOP.md）

| 前置 | 说明 |
|---|---|
| TTL 串口 root | 115200 8N1 / 3.3V；先全分区备份（mtd0/2/5/6/9/13） |
