# 参考仓库对比：`qwe-qaq/Actions-OpenWrt-AN758X` vs 本仓库

> 分析时间 2026-10-18。参考仓库：24 star / 41 fork / 2026-09-23 建，最近推送 10-17。
> 本文只记录**可执行的差异**，不做泛泛评价。

## 0. 一句话结论

他们是**轻量 overlay + 构建时下载源码**，我们是 **fork 全量**。
配置层面他们已经把该开的都开了（MOLD / SSTRIP / fullcone / UBIFS fixup / 中文包 / pon-frontend 我们都有），
**真正的差距只有一处：工具链缓存**。其余是"锦上添花"和"他们踩过的坑记录"。

我们的实测基线（run 39038544304）：

```
总时长 3h13m
  编译      14:05:03 → 17:07:52   3h02m49s   ← 占 94%
  其它 20 步合计                    11 分钟
```

**优化除编译以外的任何步骤都是无效功。** 唯一有意义的杠杆是工具链。

## 1. 架构差异

| 维度 | 他们 | 我们 | 谁更好 |
|---|---|---|---|
| 仓库形态 | 轻量 overlay（`configs/` + `diy-part*.sh` + `files/`），构建时 `git clone` 源码 | fork 全量 ponwrt，增量提交 | 各有取舍：他们小、可换源；我们能改源码、能提 PR |
| 配置方式 | 源码基座 `.config` + `cat >>` 追加机型 delta | `kconfig.pl` 三层链式合并 | **我们更好**：不产生重复键，语义明确，上游官方工具 |
| 机型裁剪 | `sed -i '/CONFIG_TARGET_DEVICE_/d'` 全删 + 追加一个 | 显式列 10 个 `is not set` | **他们更抗上游新增机型** |
| 每机型配置 | 13 个机型 × 475 行几乎重复的完整 delta | 2 个 device 共用 1 份 42 行 profile 层 | **我们更好**：维护成本低 |
| 工具链 | **actions/cache 缓存 `staging_dir/host*` + `tool*`**，key = `md5(tools/ + toolchain/ 的 Makefile)`；miss 时回退 **Release 资产备份** | 无，每次全量编 | **他们明显更好** |
| ccache | 默认关（`USE_CCACHE=false`），可选开，有完整兜底 | 默认开，key 带 `run_id` | 各有问题，见 §3 |
| 缓存 key | 年+周号（`date +%Y%W`） | commit hash + `run_id` | **他们更好** |
| 缓存保活 | 独立 workflow，每 5 天 `lookup-only` touch | 无 | **他们更好** |
| 磁盘 | 固定 `/workdir` + 8G swap | 条件切 `/mnt` 大盘 + 28GB 闸门 | 平手 |
| 并发 | 按 `MemAvailable` 动态算 `-j`，防 OOM | `nproc+1` | **他们更稳** |
| 下载 | 3 次重试 + 清理 <1KB 残包 + 工具链三大件强校验 | 单次 | **他们更好** |
| 断言 | defconfig 后校验 PON 包/第三方插件/机型，带包目录诊断 | `assert-config.sh` 校验 device 数/锚点包/br_netfilter | 我们覆盖更全，他们诊断更细 |
| 产物校验 | 无（只上传） | `profiles.json` + `must have sysupgrade` + `strings` 抽 DTB model | **我们更好** |
| 分流 | `diy-part1.sh` 里一堆 `ADD_*=false` 开关 | 编译期 `proxy=passwall\|openclash\|none` | **我们更好**（配置层，可断言） |
| PON 看门狗 | 无 | `pon-watchdog`（针对 Issue #42） | **我们有** |
| Release | 固定 tag 滚动覆盖 + 自动删旧 | 按版本打 tag，可追溯 | 我们可追溯；他们省事 |

## 2. 值得借鉴的（按收益排序）

### ★★★ P0：工具链缓存（唯一真正省时间的）

```yaml
# key 用 tools/toolchain 的 Makefile 哈希，源码不变就一直命中
TOOLS_HASH=$(find tools toolchain -type f \( -name Makefile -o -name '*.mk' \) \
             -exec md5sum {} + | sort | md5sum | cut -d' ' -f1)
CACHE_KEY="ponwrt-toolchain-${TARGET}-${SUBTARGET}-${TOOLS_HASH:0:16}"

# 缓存对象（不是 build_dir，是 staging_dir 的 host/tool）
path: |
  ${{ env.SRC }}/staging_dir/host*
  ${{ env.SRC }}/staging_dir/tool*
```

**为什么这条最值**：OpenWrt 的 host tools + 交叉工具链是固定成本，4 核上约 40–70 分钟，
且与"改了哪个包"无关。缓存它能把 3h02m 压到约 2h。再叠 ccache 命中，可到 1h30m–1h50m。

**必须配套的两件事**（他们踩过，我们也一定会踩）：

1. **`make tools/download toolchain/download` 必须在编工具链之前**
   —— `make toolchain/install` **不会**自动补下载，只会去解压 `dl/` 里已有的包，
   报错是 `Can't open dl/musl-1.2.6.tar.gz`。
2. **ccache 与工具链缓存的冲突**：`tools/Makefile` 里
   `ifneq ($(CONFIG_CCACHE)$(CONFIG_SDK),)` 才编 `tools/ccache`。
   如果工具链缓存是"未开 ccache"时建立的，命中后跳过 `make tools/install`，
   `staging_dir/host/bin/ccache` 就不存在，而 `rules.mk` 的 `TARGET_CC := ccache $(TARGET_CC)`
   仍会调它 → `.../bin/ccache: not found (Error 127)`，**整个构建失败**。
   他们的兜底：单独 `make tools/ccache/install`，失败就自动把 `CONFIG_CCACHE` 关掉继续编。

**加一层 Release 备份**（绕开 10GB 配额）：
把工具链 tar 成 `${CACHE_KEY}.tzst` 传到固定 tag `toolchain-cache` 的 Release 里，
actions/cache miss 时从那里下载解压，再回写 cache。同一平台旧资产自动删除。

### ★★ P1：缓存 key 改成「年+周」

他们注释原文：

> 若用 `run_*`，每次运行都会 save 一份新副本，10GB 配额很快被刷满并淘汰掉真正有用的旧缓存；
> 改用周号后同一周内复用同一条目。

我们现在 `cc-<hash>-<run_id>` —— 每跑一次存一份新副本，会挤掉 `dl`。
实测当前仓库已有 3 个缓存条目 / 3GB，再跑几次就会开始互相淘汰。

### ★★ P1：缓存保活

`actions/cache` 的条目 **7 天不访问即回收**。加一个 5 天一次的 workflow：

```yaml
- uses: actions/cache/restore@v4
  with:
    path: /tmp/dummy
    key: ponwrt-toolchain-
    lookup-only: true      # 只检查不下载，几秒完成
```

### ★ P2：download 重试 + 残包清理

```sh
for i in 1 2 3; do make download -j8 && break; sleep 5; done
find dl -size -1024c -type f -delete    # 下载中断留下的半截包，解压时报 "does not look like a tar archive"
```

### ★ P2：动态并发（防 OOM）

```sh
JOBS=$(awk -v p="$(nproc)" '/^MemAvailable:/{m=int($2/2097152)+1} END{print m<p?m:p}' /proc/meminfo)
```
每个 cc1 约 1.5–2GB RSS，4 核 16G 上 `-j8` 容易被 OOM killer 杀掉，报错还很难看懂。

### ★ P2：机型裁剪改成「全删 + 追加」

```sh
sed -i '/CONFIG_TARGET_DEVICE_/d; /^CONFIG_TARGET_MULTI_PROFILE=/d' .config
printf 'CONFIG_TARGET_MULTI_PROFILE=y\nCONFIG_TARGET_DEVICE_airoha_%s_DEVICE_%s=y\n' "$SOC" "$PROFILE" >> .config
```
比我们列 10 个 `is not set` 更抗上游新增机型（上游加第 13 个机型时我们不会漏关）。

### ★ P3：第三方状态插件（功能缺口，非性能）

| 插件 | 来源 | 作用 |
|---|---|---|
| `luci-app-airoha-npu` | `luanmuc/luci-app-airoha-npu` | NPU 卸载状态 / CPU 频率 / Frame Engine / PPE 流表 |
| `luci-app-pon-status` | `qwe3017/luci-app`（monorepo） | PON 光模块卡片：收发光/温度/电流/电压 |
| `luci-app-natmode` | 同上 | NAT 类型三选一（全锥形/受限/对称） |

`luci-app-airoha-npu` 有个**必踩的坑**（他们已解决）：`po/zh_Hans/luci-app-airoha-npu.po`
必须改名成 `airoha-npu.po`。因为 `luci.mk` 用 `basename(po)` 生成 lmo 名，
而运行时按 `LUCI_BASENAME`（= `airoha-npu`）查找，不改名中文不生效。

### ★ P3：`/sbin/tempinfo`（概览页温度）

autocore 调 `/sbin/tempinfo` 填 LuCI 概览页的「温度」行。他们的版本能出
`CPU: 58.7°C, WiFi: 46.0°C 48.0°C, PON: 48.5°C`。
顺带给出 `ponctl status --json` 的字段路径（可直接用于我们自己的诊断/看门狗降级）：

```
@.frontend.temperature_celsius   @.frontend.tx_power_dbm
@.frontend.rx_power_dbm          @.frontend.tx_bias_ma
@.frontend.voltage_volts
```

### ★ P3：`96-wifi-5g-cn`

CN 国家码 + `country_ie=1` + `htmode=HE160`，并用 `iw phy <phy> info | grep '160 MHz'`
探测能力，不支持才回落 HE80。我们默认关 WiFi，一旦打开就需要这个。

## 3. 他们做错 / 我们不该照抄的

| 项 | 问题 |
|---|---|
| `USE_CCACHE=false` 默认关 | 他们靠工具链缓存省时间，把 ccache 当可选项。我们已有 ccache 且工作正常，**两个杠杆叠加才对**（但要处理 §2 的 Error 127） |
| 每机型 475 行完整 delta | 13 个机型 = 13 份几乎一样的文件。改一个公共包要改 13 处 |
| `cat >> .config` 覆盖 | 依赖 kconfig "后写覆盖先写"，但会留下重复键；`make defconfig` 之后排查困难。`kconfig.pl` 是上游官方工具 |
| Release 固定 tag 滚动覆盖 + 自动删旧 | 省事，但**无法回溯**"某次刷的到底是哪一版"。我们按版本打 tag 更安全 |
| 删旧 workflow run / 旧 release | 个人仓库可以，但历史价值被丢掉 |

## 4. 我们比他们强、不要为了抄而退化的

- **fork 全量** → 能直接改源码、能向上游提 PR
- **`kconfig.pl` 分层 + 断言** → 不产生重复键，断言在 30 秒内失败而不是烧 3 小时
- **`pon-watchdog`** → 他们没有；针对 Issue #42 的 10G-EPON 冷启动自循环
- **编译期三选一分流层** → `proxy=passwall|openclash|none`，配置层实现且可断言
- **产物三重校验** → `profiles.json` device 数 + 必须有 sysupgrade + `strings` 抽 DTB model
- **完整配置随产物发布** → `config.buildinfo` + `config.full` + `sha256sums.txt`

## 5. 他们文档里对我们有用的事实

1. **daed 的 BTF 开关组合**（如果他们以后想回 daed）：
   ```
   CONFIG_KERNEL_DEBUG_INFO_BTF=y
   CONFIG_KERNEL_MODULE_ALLOW_BTF_MISMATCH=y
   CONFIG_KERNEL_BPF=y
   CONFIG_KERNEL_BPF_SYSCALL=y
   CONFIG_KERNEL_BPF_EVENTS=y
   ```
   基线里只有 `DEBUG_INFO`（且 `DEBUG_INFO_REDUCED=y`），**未开 BTF**，所以 daed 确实跑不了。
2. **`fitblk` 在基座里是 `=m`**（只编不装），要装进 rootfs 必须显式 `=y`——我们已 pin，正确。
3. **`make toolchain/install` 不自动下载源码包**（见 §2 P0 第 1 条）。
4. **`tools/ccache` 只在 `CONFIG_CCACHE` 生效时才编**（见 §2 P0 第 2 条）。
5. `actions/checkout@v5`、`actions/cache@v5`、`upload-artifact@v5` 已可用（我们用的是 v6/v4/v4，也能跑）。

## 6. 建议的落地顺序

**第一步（低风险、高收益，只动 CI）**
1. 工具链缓存（`staging_dir/host*` + `tool*`）+ Release 备份兜底
2. 补 `make tools/download toolchain/download` + 工具链三大件校验
3. ccache 与工具链缓存的冲突兜底（缺二进制就补装，再失败就关 ccache）
4. 缓存 key 改周号
5. 缓存保活 workflow
6. download 重试 + 残包清理
7. 动态 `-j`

预期：3h02m → **2h 以内**（工具链命中），再叠 ccache 命中可到 **1h30m–1h50m**。

**第二步（功能层，需要确认是否要）**
- `luci-app-airoha-npu` / `luci-app-pon-status` / `luci-app-natmode`
- `/sbin/tempinfo`
- `96-wifi-5g-cn`

**不建议做**：改成 overlay 仓库、`cat >>` 覆盖、固定 tag 滚动 Release。
