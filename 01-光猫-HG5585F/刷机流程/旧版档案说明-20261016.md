## 0. 一句话

设备是 **烽火 HG5585F 联通版，10G-EPON 非对称（10G 下 / 1G 上），AN7581 SoC**。
ponwrt 驱动支持 `epon-10g-1g`（状态 ✅ 已实测）—— **刷 OpenWrt 路线可行**。
**卡点只剩两块原始字节：APONCAL 光模块校准（2KB）和 MT7916 WiFi EEPROM（4KB）**，都在 `mtd13 factory` 里，需 root 或 TTL 串口导出。

## 7. `/fh_tool/api` 私有维护接口

烽火通用维护接口，**本机在 80 端口**（恩山验证的 CT 版在 8080，本机 8080 不开）。
AES 密钥从 MAC 派生 —— 这只是报文编码，**不是身份认证**，仅限自家 LAN 使用。

```python
h   = sha256("D069FF163280").hexdigest()      # 64 小写 hex
key = ''.join(h[2*i+2] for i in range(16))     # defb7190b3a328c8
iv  = ''.join(h[3*i+3] for i in range(16))     # cff1cb634c1f5616
# 紧凑 JSON → AES-128-CBC/PKCS#7 → base64 → POST /fh_tool/api, Content-Type: text/plain
# 响应反向解密，检查 result == 0
```

| 调用 | 加密前明文 | 用途 |
|---|---|---|
| 只读 | `{"index":"1","func":"GetDevInfo"}` | 回读版本 / serialnum / port_num |
| 只读 | `{"index":"1","func":"GetTelnetInfo"}` | Telnet 状态（`info4` 不是口令） |
| 写 | `{"index":"1","func":"TelnetEnable","telnet":"1"}` | 开 23 端口（已实测有效） |

工具：`tools/fhtool_probe.py`（只读探测）、`tools/fhtool_telnet.py`（开 Telnet + 验握手 + 读回）

> 恩山原帖的持久化命令 `cfg_cmd set InternetGatewayDevice.DeviceInfo.X_CT-COM_ServiceManage.TelnetEnable 1`
> **对联通固件无效**——`X_CT-COM_*` 是中国电信 TR-069 私有节点，本机 `GetParamVal error -1`（节点不存在）。
> `X_FH_TelnetForceOffTime` 节点存在但值为空 → 24 小时强制关闭**大概率未启用**。

## 8. ❌ 未能取到的数据（刷机前必须解决）

`mtd13 "factory"` = `0x300000`（3 MiB）。ponwrt `03_pon_data` 声明 `pon_data_target factory ubi 1048576`（1 MiB），
差值由 `fiberhome-factory` 工具转换。

| 偏移 | 大小 | 内容 | 状态 |
|---|---|---|---|
| `0x000000` | 2 KB | **APONCAL 光模块校准** | ❌ **缺这个 PON 起不来** |
| `0x000800` | 2 KB | 保留 | — |
| `0x001000` | 4 KB | **MT7916 WiFi EEPROM** | ❌ 缺这个 WiFi 起不来 |
| `0x002000` | 6 B | Base MAC | ✅ 已知 |
| `0x002010` | 8 B | PON SN | ✅ 已知 |
| `0x002020` | 32 B | 整机 SN | ✅ 已知 |

### 为什么取不到

Telnet shell 是**真·非 root**：

```
Uid: 100 100 100 100   (opuser)
CapPrm / CapEff: 0000000000000000     ← 零 capability
/dev/mtd13 = crw-rw---- root root      ← EACCES
```

**几乎全部 SUID = 0**（`/usr/bin`、`/usr/sbin`、`/fhrom/bin` 全是 root:root 755/777）；唯一例外是 `/bin/busybox`（`-rwsr-xr-x`），但它对普通 applet 会主动降权——实测 `/bin/busybox cat /proc/self/status` 仍是 `Uid: 100`，不能直接借它提权。

> **2026-10-19 补充**：`/fhrom/bin/su_tool` 是**软件升级配置工具**（字符串里是 usrconfig/preconfig、`TelnetPassword` 等），不是 `su` 认证助手；`/fhrom/fhshell/set_root_passwd.sh` 只负责把参数写进 `/var/tel_passwd`，而改 `/var/tel_passwd` 或 `/etc/shadow` 对 `su` 均无效（未 strace 确认它实际读哪个文件）。

`an758x-stock2ubi` 需要 root 运行 → telnet 路线到此为止。

**已试过并失败的提权路径**（记录以免重复踩）：

| 尝试 | 结果 |
|---|---|
| `/fhrom/bin/su_tool` | 无输出，仍 opuser；后续确认它是软件升级配置工具，不是 su 认证 |
| telnet `su` + 恩山密码 `Fh@`+MAC 后六位（及 `.81`–`.84` 派生 MAC、PON SN/设备 SN 变体） | 全部 `su: incorrect password`（2026-10-19 实测） |
| 改 `/etc/shadow` 的 root `$6$` 哈希，或在 `/var/tel_passwd` 加 root 行（哈希/明文） | `su` 仍拒绝 → 改这两个文件对 su 无效（未 strace 确认它实际读哪里） |
| 工厂 CLI `generate rootkey` | 返回 success，但 key 不打印、`/fhconf/fh_key_conf` 为空，不能直接当 su 口令 |
| web 超管 `do_ping` 命令注入（`;` / `$()`） | `;` 在 `$host` 变量展开中不构成命令分隔符；`$()` 被后端过滤，未执行 → 不可用 |
| 往 `/var/tel_passwd`（= `/tmp/tel_passwd`，telnetd 实际读的认证文件）追加 root 行 | telnetd 拒绝，口令必须 `$5$fh$` SHA-256 crypt；用 admin 同一串哈希仍被拒 |
| 同步改 `/etc/shadow`（= `/tmp/shadow`）root 的 `$6$` SHA-512 哈希 | 仍拒绝 → telnetd 除 passwd 外还有校验 |
| `mv -f` 覆盖 root 拥有的文件 | ✅ **可行**（`/tmp` 是 777 **无 sticky 位**，`rename()` 可覆盖）。是上面两条的技术前提 |
| wrapper 命令黑名单 | 拦：`dd` `rm` `cp` `ln` `head` `uname` `which` `id` `df`。放行：`ls` `cat` `echo` `grep` `wc` `mv` `tar` `sed` `openssl` |

> ⚠️ 上述 `/var/tel_passwd` 与 `/etc/shadow` 的改动**已全部还原**，原值备份在设备 `/tmp/tel_passwd.bak`、`/tmp/shadow.bak`。

### 可行路线

> ⚠️ **关于「网页后台上传 fip」**：恩山/mao.fan 的 HG5382A 流程里，那个上传页是 `an758x-stock2ubi` 在 **`:3333`** 起的临时网页，**必须先 telnet `su` 到 root 再运行它**；不是原厂超管（192.168.1.1）的「固件升级」页。原厂超管升级页走 `/fh_api/tmp/FHUPAPIS?action=upgradeimage`，从页面/接口看是 FiberHome 固件升级用途，不是 stock2ubi 的 fip 上传页（未实测用该页上传裸 fip；不要把它当安全路径）。本机 CU 固件的 `su` 密码未知，所以「只登录 web 超管就能上传 fip」在本机不成立。

1. **TTL 串口**（推荐，无需 root）：`uboot-an758x` 手动路径 —— 串口进 bootloader，写 preloader/bl31，
   拿 `http://192.168.0.1/` 的 U-Boot Web recovery。需拆机 + 3.3V USB-TTL 线；**过程中断网**（光纤重新注册几十秒）。
   `an758x-stock2ubi` release `v0.1.14`、uboot release `v2026.07-4`。
2. **先拿 CT 那台试刀**（更安全）：CT 未注册、2.5G 口，练手不丢宽带。
3. 攒够身份数据后，若确能接受风险，可评估「从同型号其它设备 factory 移植」——但 **APONCAL 与光模块强绑定，跨机不可行**。

## 10. 源码与 CI 选型（重要）

| 仓库 | 最新提交 | 日期 | 结论 |
|---|---|---|---|
| `huladabang/ponwrt`（恩山帖给的 fork） | `c3b518ba` | 2026-09-29 | ❌ **落后 10 天，别用** |
| `pbs05/ponwrt`（上游） | `a57faf93` | 2026-10-09 | ✅ **用这个** |

**fork 缺的上游已合并内容里有一条致命项**（PR #21，10-05 合入）：
> HG5585F 的 reset 键 DTS 指向 GPIO0，而 GPIO0 实际是 `uart1_txd`，**没接到按键**。
> 实测按键是 **GPIO35**（`GPIO_DATA1` bit 3），U-Boot 那边一直用 GPIO35。

在 fork 上刷出来的固件，**reset 键无效 → U-Boot HTTP recovery 进不去**，而那是刷固件失败时唯一的救命通道。

**云编译仓库 `qwpianzhang/Actions-OpenWrt-HG5585F`**：默认源码是 `qwe3017/ponwrt`，跑之前把 workflow 的
`source` 输入项切成 **`pbs05/ponwrt`**，`profile` 选 `fiberhome_hg5585f-cu`。

**CT 机型另有一个未合补丁**（PR #34，open）：MaxLinear GPY211C 2.5G 口 reset 时序竞态，
热重启时 `lan1` 会 NO-CARRIER 到下次冷启动。修法是 DTS 写死 `ethernet-phy-id67c9.de10`。
