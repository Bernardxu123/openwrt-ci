### 2.5 【事实/证据】密钥/口令派生（与本项目既有脚本**逐字一致**）

```python
def derive_key_iv(mac):
    h = hashlib.sha256(mac.encode("ascii")).hexdigest()
    key = "".join(h[2*i+2] for i in range(16)).encode("ascii")   # 16 个 ASCII 字符
    iv  = "".join(h[3*i+3] for i in range(16)).encode("ascii")   # 16 个 ASCII 字符
    return key, iv
```

`co_names = ('hashlib','sha256','encode','hexdigest','join','range')`，
两个 `<genexpr>` 的常量分别是 `2` 和 `3` —— 与 `脚本/fhtool-ct.py` 的 `derive()` **算法完全相同**（那是一份已知的 CU 机实现，说明这套算法在 CU/CT 两版固件上是同一套）。

报文格式（`tool_call`，`co_flags` 含 `VARKEYWORDS` → 签名是 `**params: str`）：

```
明文 = json.dumps({"index":"1","func":func, **params}, separators=(',',':'), ensure_ascii=False)
body = base64( AES-128-CBC-PKCS7(明文, key, iv) )
POST /fh_tool/api   Content-Type: text/plain   Connection: close   timeout=6s   ProxyHandler({})
响应 = base64(AES 密文) → 解密 → JSON；要求 str(result.get('result')) == '0'
```

**AES 由子进程完成**（这是全篇最值得记的一条行为）：

- Windows：`subprocess.run(['powershell.exe','-NoProfile','-NonInteractive','-Command', POWERSHELL_AES], input=<JSON>, text=True, capture_output=True, timeout=15, check=True)`
  - `POWERSHELL_AES` 是一段**内联固定脚本**（852 字符，`co_consts[7]` 原文），用 `[System.Security.Cryptography.Aes]::Create()` 做 CBC/PKCS7
- 非 Windows：`openssl enc -e|-d -aes-128-cbc -K <hex> -iv <hex> -nosalt`

【风险】每次 API 调用都会起 2 个子进程（请求加密 + 响应解密）。**这不是"下载后执行"**，脚本内容硬编码在 pyc 里、不落盘、不联网，但会在父进程命令行里带出 `-Command <脚本>`。安全软件可能因此弹"可疑 PowerShell 行为"——**属正常现象，不是它想做坏事**。

### Q4 对 CT V2 固件是否可能有效？与已知 CU `/fh_tool/api` 行为是否一致？

**结论：可用但有前提（"可能有效"，本报告不做"已验证可用"的断言）。**

一致的地方（**支持"可能有效"**）：
1. 接口路径、报文结构、`index/func` 字段、AES-CBC+base64 编排、**key/iv 由 MAC 的 SHA-256 派生** —— 与 `脚本/fhtool-ct.py` 里那份 CU 机实现**完全一致**，说明这是烽火两版固件共用的私有维护接口。
2. `func` 名 `GetDevInfo` / `TelnetEnable` 与 CU 机已知可用名一致。
3. 工具自带 **CT 专用硬闸门**：两个持久化路径都带 `X_CT-COM_` 前缀（电信私有数据模型，联通用的是另一套前缀），且版本闸门是 `V4.2.0 / 24FHW45000` —— 说明作者是**针对 CT V2 写的**，不是 CU 工具改个名字。

不一致 / 新增的地方（**需要注意**）：
1. **持久化动作是新增的**：已知 CU 机 `/fh_tool/api` 的 `TelnetEnable` 只写运行时，重启失效。本工具额外用 Telnet + `cfg_cmd` 去写两条 TR-069 开关，**这是作者自己补的"重启后自动开"逻辑**，固件是否接受这两条路径、写入后是否真能持久化，**静态无法证实，只能由设备验证**。
2. **Web 端口是 8080 硬默认**（不是 80）。若 CT V2 的 Web 在 80，工具会在第 3 步（`local_ip_for` 连 8080）就 `raise 无法连接`；此时需要 `--web-port 80`。**这一点必须在实机上先确认，否则会误判"工具不工作"**。
3. 默认 Telnet 用户 `telnetadmin` / 口令 `FH-nE7jA%5m`+MAC末6位 —— 这是烽火**出厂默认**，若设备已改过口令，第 14-16 步会失败（但此时 Telnet 已经开着，可以手工登录）。

**风险（按严重度）**：
- 【中】**第 11 步成功、第 16 步失败** → 设备已被运行时开 Telnet（可接受），但持久化没成，属于"半成功"状态。工具会报错退出，不会继续乱写。
- 【中】`cfg_cmd set` 是**对未知 shell 下发未知命令**。若该固件 shell 不认 `cfg_cmd`，最多回显 `command not found`，工具报"持久化写入失败"。**CE 风险低但不能排除**（我们没在实机验证过这个 shell）。
- 【低】**版本闸门是硬编码的**，这是个**加分项**：在不匹配的固件上它会在第 9 步就中止，**不会误操作**。反过来说，如果目标 CT V2 的版本号不是 `24FHW45000`（新批次/新版本），工具会直接拒绝——**那时不是"工具坏了"，而是闸门在起作用**。

### Q5 Tftpd64 是否可信？

| 项 | 值 |

**【风险 / 残留未知】**
- 上游**不签名**，所以"未被二次打包"**无法只靠静态特征证明**。要坐实，需从官方源（`tftpd64.coulondre.org` 或 GitHub `PJO2/tftpd64`）取一份 4.64 包，比对 `SHA256=34DE53B4…90E4E7`。
- 4.64 是 2019 年的版本，上游后续有 4.7x。**旧版本本身不是安全问题**（TFTP 协议几十年没变），但缺后续修补。

### Q6 使用建议：能不能在 Windows 实机跑？隔离措施？替代方案？

**建议：不要在主力 Windows 实机上双击运行。** 理由不是"发现恶意行为"（没发现），而是：
1. 无签名 + 无版本信息 + 作者只留一个 QQ 号 → 来源不可审计；
2. 它会起 `powershell.exe` 子进程（企业/杀软环境会告警，也确实是攻击面）；
3. 它会**改设备的持久化配置**（第 14-17 步），不是纯读；
4. 出问题时你无法区分"工具行为"还是"固件行为"。

#### 推荐的替代方案（**优先**）

用我们自己的 `光猫-CT-HG5585F/脚本/fhtool-ct.py` 扩展两个能力，全程可审计、纯 Python：

| 需要补的 | 怎么做 | 依据 |
|---|---|---|
| MAC 自动读取（免手抄） | `GET http://<ip>:8080/cgi-bin/ajax?ajaxmethod=web_get_brmad` → JSON `.brmad` | 本报告 §2.4 第 5 步 |
| 持久化开关 | Telnet 登录后对两条 `X_CT-COM_ServiceManage(.Lan).TelnetEnable` 下发 `cfg_cmd set <path> 1`，再 `cfg_cmd get` 校验 `value=1` | 本报告 §2.4 第 16 步 |

> 现有 `fhtool-ct.py` 的 `derive()` / `call()` 已经和本工具**逐字算法一致**，只差上面两块。这项改动**不在本任务写作用域内**，需要另开任务。

#### 如果坚持要用这个 EXE —— 最少隔离清单

1. **先只读**：`HG5585F-CT-V2一键开Telnet.exe --host 192.168.1.1 --web-port 8080 --probe`
   → 到第 9 步就结束，**不改设备**。这一步能确认「8080 端口对不对 / `web_get_brmad` 通不通 / 版本号是不是 `V4.2.0`+`24FHW45000`」。
2. **网络隔离**：PC 与光猫**单独一根网线直连**；PC 关 WiFi、禁用其他网卡、不要连家里 LAN/WAN。工具本身不需要外网。
3. **账号隔离**：用 **Windows 沙箱 / 一次性虚拟机 / 标准用户** 跑（`powershell.exe` 需要 FullLanguage，ConstrainedLanguage 下 AES 会失败，所以不要靠 AppLocker 限制 PS）。
4. **抓包**：跑之前开 Wireshark，过滤器 `host 192.168.1.1`。跑完检查：**只应有 8080 的 HTTP 和 23 的 Telnet**，不应有任何其他目标。这是最直接的"它有没有偷偷外联"验证。
5. **跑前备份**：先按 `03-身份采集与备份.md` 做完身份数据备份，再动设备。
6. **跑后收尾**：立刻把 Telnet 关掉（Web 后台，或再调一次 `TelnetEnable` 传 `telnet=0`），改掉默认口令，**断开直连、恢复日常网络**。
7. **需要"重启后自动开"时**：优先用 `--runtime-only`（第 13 步就结束，不碰 `cfg_cmd`），把持久化留到看清效果之后再做。

#### 关于 Tftpd64

- **能用**，但建议：从官方源重下 4.64（或更新版），比对 `SHA256=34DE53B43C32E3ED5231A57683103ACAD1AEBEEF08309CF8E770C27ACC90E4E7`；若一致就用这份。
- 用法约束：**只绑 `192.168.x.x`**、**只在刷机那几分钟开着**、**不要同时开 DHCP/DNS/Syslog 服务**（刷 uboot 只用到 TFTP）、刷完立刻退出。
- 其实 `an758x-stock2ubi` 也可以走 uboot 的 `tftpboot` 由 **Linux 侧 `tftpd-hpa`** 或 Python 的 `tftpy` 提供——如果只是想避免第三方 Windows 二进制，这是更干净的路线。
