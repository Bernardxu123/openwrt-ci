### 0.2 主路由上根本没有 `iw`，`iw dev ... scan` / `station dump` 全部不可用

- `command -v iw` → **MISSING**；有的是 `iwconfig` / `iwinfo` / `iwpriv` / `iwlist`（busybox 外挂）。
- `iwlist ra0 scan` → `Interface doesn't support scanning.`（MediaTek mt_wifi 驱动不上 wext 扫描）。
- 因此本报告用等价手段替代：
  - `iw dev ra0 info` → `iwconfig ra0` + `iwinfo ra0 info`
  - `iw dev ra0 station dump` → `iwinfo ra0 assoclist`（含 RSSI / RX/TX 速率 / MCS / 带宽）
  - `iw dev ra0 scan` → `iwpriv ra0 get_site_survey`（见 0.3）+ **小米 AP 侧全频段 `iwlist wl1 scan` / `wl0 scan`**（该驱动支持全频段扫描，用它拿到真实信道分布）

### 0.3 mt_wifi 的 `get_site_survey` 的 "Ch" 列有驱动缺陷（不影响结论，但要正确解读）

主路由 `iwpriv ra0 get_site_survey` 返回 `Total=33`，但 **33 行全部被标成 `Ch 6`**；`iwpriv rai0 get_site_survey` 返回 `Total=7`，**7 行全部标成 `Ch 36`**。

交叉验证：
- AP 侧全频段 `iwlist wl1 scan` 扫到 **32** 个 2.4G cell，5G 侧扫到 **9** 个；
- 主路由 2.4G `Total=33` ≈ 32（全频段总数），5G `Total=7` ≈ 9（数量级一致）。

→ 结论：**该 survey 覆盖全频段，但 "Ch" 列被错误地统一填成当前信道**。它可以用来读「BSSID / SSID / 信号强度 / W-Mode / 隐藏 SSID」，**不能用来读每条记录的信道**。信道归属一律以 AP 侧 `iwlist scan` 为准。

（列含义已解出：`No | Ch | SSID | BSSID | Security | Signal% | Signal2% | W-Mode | ExtCH | NT(=In) | SSID_Len | WPS | DPID | BcnRept | MDId | FToverDS | RsrReqCap`；例如 `In 10` 表示 SSID 长度 10（`bernard_5G`），`In 0` 表示隐藏 SSID。）

## 4. 重叠 / 干扰判定

### 4.1 5G：ch36/160 vs AP ch36/160 —— 🔴 **完全重叠（100 %）**

| 发射源 | 类型 | 频段 |
|---|---|---|
| 主路由 `rai0` | AP | 5170–5330 MHz（ch36–64） |
| 小米 AP `wl0`（`bernard_5G`） | AP | 5170–5330 MHz（ch36–64） |
| 小米 AP `wl5`（`MiMesh_ed038d3f2` 隐藏） | AP | 5170–5330 MHz（ch36–64） |

- 两个**可见**主 SSID（`bernard_5G` ×2，BSSID `70:D5:1E:06:9C:7F` vs `A4:A9:30:81:E9:31`）在**完全相同的信道 + 完全相同的 160 MHz 块**上。AP 扫到主路由 -56 dBm，主路由扫到 AP 57 % —— 互相都强到能听见对方。
- **技术细节（为什么 160 MHz 尤其致命）**：IEEE 802.11 的 160 MHz 只有 **primary 80 MHz 块做竞争退避**，secondary 80 MHz **不做保护**。两个 160 MHz AP 同块时：
  1. primary 块（5170–5250）两台要互相退避 → 每台只拿到 ~50 % 的 primary 竞争时隙；
  2. secondary 块（5250–5330）两台**同时发射就碰撞**，且碰撞后仍要在 primary 上重新抢 —— 实际吞吐远低于标称 2401 Mbps。
- **隐藏的第三个发射源**：AP 的 `wl5`（MiMesh 回程 SSID，无线回程根本没在用）也在同块做 160 MHz 发射，等于**白白多加一路同频干扰源**。
- 旁证：`rai0` 的 Tx fail PER **20.3 %**、Rx with CRC PER **46.1 %**；`Last TX Rate = NSS2_MCS4, BW160/8080` —— 160 MHz 链路跑在 MCS4（2SS 下 MCS4/11 ≈ 36 % 调制），说明链路本身在丢包重传中苟活。

### 4.2 2.4G：主路由 ch6/HE20 vs AP HT40(ch1+ch5) —— ⚠️ **高度重叠（~75 %）**

| 发射源 | 频段 |
|---|---|
| 主路由 `ra0` ch6/HE20 | 2427–2447 MHz |
| 小米 AP `wl1` + `wl13` + `wl4`（3 个 40 MHz 载波，center1 2422 = ch3，primary ch1 + secondary ch5） | 2402–2442 MHz |

- 主路由 ch6 的 20 MHz 落在 AP 40 MHz 载波的**上边沿**：重叠区间 2427–2442 MHz = **15 MHz / 20 MHz = 75 %**（主路由的 ch6 几乎完全泡在 AP 的 secondary(ch5) 半边里）。
- AP 侧一次开了 **3 个同频 40 MHz 发射源**（主 SSID `bernard` / MIoT 隔离 SSID / 隐藏 MiMesh），等于在 ch1–9 区间泼了三层 40 MHz 底噪。
- 旁证：`ra0` 的 **Rx with CRC PER 54.0 %**、Tx fail PER 23.4 %；`wl1` invalid nwid=5541、`wl4` invalid nwid=22400；最弱的 `chunmi-microwave`（-83 dBm）只有 MCS2/6 Mbps。
- 2.4G 干扰不会像 5G 那样立刻体现为吞吐腰斩，但它主要伤害**边缘 IoT**（微波炉、扫地机、空气炸锅这类低功耗 + 弱信号设备），表现为反复重连 / 掉线。

### 4.3 额外发现：同 SSID 双 BSSID 的「乒乓」风险

`52:35:01:99:73:1e`（SGT-AL10）**同时出现在**主路由 `ra0`（-67 dBm）和 AP `wl1`（-72 dBm）的关联表里。同 SSID、不同信道的两个 BSSID 会让这类客户端在两个 RADIO 之间反复 re-associate（每次切换都断 1–3 秒）。改信道时要注意这会放大/缩小乒乓现象。

## 5. 中国大陆 CN 域下 5G 160 MHz 的可用信道情况

### 5.1 先纠正一个前提

> 任务描述里写「160 MHz 需要 **5 个连续 80 MHz 块**」—— **不对**。
> 正确说法：**160 MHz = 2 个连续 80 MHz 块 = 8 个连续 20 MHz 信道**（802.11ac/ax 的 160 MHz 就是 primary 80 + secondary 80）。
> 5 GHz 里「连续 80 MHz 块」总共只有 6 个，160 MHz 是从这 6 个里挑**相邻的 2 个**。

### 5.2 CN 域下 5 GHz 信道结构（来自设备自身 regulatory 表，非推测）

AP 的 `iw list`（`phy5` = AP 的 5G，country=CN）Band 2 频率表：

```
* 5180 [36] (33 dBm)   * 5200 [40]   * 5220 [44]   * 5240 [48]
* 5260 [52] (33 dBm)   * 5280 [56]   * 5300 [60]   * 5320 [64]
* 5745 [149](33 dBm)   * 5765 [153]  * 5785 [157]  * 5805 [161]  * 5825 [165]
```
（`mld-phy0` 的 Band 2 另外还列出 100/104/108/112/116/120/124/128/132/136/140/144；`phy5` 未列出，且 `iw list` 未暴露 DFS/NO-IR 标志 —— qcawificfg80211 驱动把 DFS 管控做在内部，表现为下面那条 `channel_block_list`。）

`phy5` 能力位：`Supported Channel Width: 160 MHz` / `short GI (160/80+80 MHz)` / `HE160, HE160/HE80+80` —— **AP 硬件支持 160 MHz**。

### 5.3 80 MHz 块与 160 MHz 块对照

| 80 MHz 块 | 中心 | 20 MHz 信道 | CN 可用性 |
|---|---|---|---|
| #1 | 42 | 36–48 | ✅ 非 DFS |
| #2 | 58 | 52–64 | ⚠️ DFS（小米已 block） |
| #3 | 106 | 100–112 | ⚠️ DFS（小米已 block） |
| #4 | 122 | 116–128 | ⚠️ DFS（小米已 block） |
| #5 | 138 | 132–144 | ⚠️ DFS（小米已 block） |
| #6 | **155** | **149–161**（5735–5815 MHz） | ✅ 非 DFS，且实测最干净 |

| 160 MHz 块 | 中心信道 | 覆盖 | CN 可用性 |
|---|---|---|---|
| A | **50** | **36–64**（5170–5330 MHz） | ✅（含 DFS 半块 52–64，实测可正常起） |
| B | 114 | 100–128 | ⚠️ 全 DFS，且小米 block |
| C | 138 | 116–144 | ⚠️ 全 DFS，且小米 block |
| — | — | **149–177** | ❌ **不存在**（149 之后只有 153/157/161/165，169/173/177 无效） |

### 5.4 三条关键结论

1. **CN 域下 160 MHz 只有一个「干净」的落点：ch36–64（center 50）。** 想做第二个 160 MHz 就必须进 DFS 段（100–144）→ 会触发雷达检测 / CAC / 静默期 / 被动换道，家庭 AP 固定主信道不该碰。
2. **149–161 只能做 80 MHz**（center 155），CN 非 DFS。本楼该段只有 1 个 -87 dBm 的弱邻居，**是全楼最干净的 5G 频谱**。
3. **小米 AP 的 `bernard_5G` 有 `channel_block_list='52,56,60,64,100,104,108,112,116,120,124,128,132,136,140,165'`**
   → App 里能选的 5G 信道只有 **36/40/44/48/149/153/157/161**；
   → 其中 **160 MHz 只有 ch36 成立**（149–161 凑不出 160 块）。

> ⇒ **「把两台错开」在 CN 下不能靠「换一个 160 信道」实现，只能靠「一方降宽到 80 MHz 并搬到 149–161」。** 这是本次方案设计的核心约束。

### 5.5 主路由侧 160 MHz 的可用性（MT7916 mt_dbdc，country=CN）

- 当前实测运行 `htmode='HE160'` @ ch36（5170–5330 MHz）**工作正常** → 说明主路由支持 CN 的 36–64 160 MHz 块。
- 主路由无 `iw`，取不到 `iw list`，无法直接枚举它的 5G 频率表；但主路由**历史上就以 `ch149 / HE80` 正常跑过**（现网文档记录），且本次实测 ch149 段在本楼最干净 → **ch149/HE80 是主路由侧经过验证的回退落点**。
- 硬性约束：**`country` 必须保持 `CN`**。若变成 `00`（global），ch149 会被判 NO-IR → 5G 直接整体消失（历史已踩过这个坑）。

## 6. 推荐信道方案

### 6.1 2.4G —— 推荐方案

| 角色 | 现值 | **改成** | 改在哪 |
|---|---|---|---|
| 主路由 `ra` | ch6 / HE20 | **ch11 / HE20**（宽度不动） | ✅ **主路由自助改**（一条 UCI） |
| 小米 AP `wifi0` | ch1 / 40MHz | **不动**（保持 ch1/40） | ⛔ 不需要动（也就避开了 App 操作风险） |

**理由**
- 主路由 ch11 = 2452–2472 MHz；AP 的 40MHz 载波 = 2402–2442 MHz → **零重叠**（中间还留 10 MHz 保护带）。
- ch11 的邻居数 9，比 AP 所在的 ch1（12 个，全楼最挤）少；而 ch6 之所以看着不挤（6 个），恰恰是因为 AP 那条 40MHz 载波把 ch6 淹了 —— 主路由搬走以后，ch1–9 整个频段都会变干净，**AP 侧那 11 个客户端也顺带受益**。
- 2.4G 全部是 IoT（微波炉/扫地机/炸锅/手机），20 MHz 足够；**不必为了 2.4G 去动小米 App**（把 AP 从 40 降到 20 只会让 AP 侧 11 个客户端白断一次，峰值速率还腰斩）。

**备选（若你更想把「污染源」也收掉）**
- 主路由保持 **ch6 / HE20**，AP 降到 **HT20 / ch11** → 同样零重叠（2427–2447 vs 2452–2472），且 ch6 的邻居最少（6 个）。
- 代价：**必须进小米 App**（不能手改 UCI，理由见 1.2），AP 侧 11 个 2.4G 客户端会断一次，AP 2.4G 峰值 688 → 344 Mbps。
- 不推荐作为首选：收益仅是「主路由少 3 个邻居」，却要付出 App 改配置 + 11 台设备断连的代价。

### 6.2 5G —— 推荐方案

| 角色 | 现值 | **改成** | 改在哪 |
|---|---|---|---|
| 主路由 `rai` | ch36 / HE160 | **ch149 / HE80** | ✅ **主路由自助改**（两条 UCI） |
| 小米 AP `wifi1` | ch36 / 160MHz | **不动**（保持 ch36/160） | ⛔ 不需要动（也就避开了 App 操作风险） |

**理由**
- 错开之后：**5170–5330 MHz 只剩 AP 一台 160 MHz 发射源**（主路由离开），**5735–5815 MHz（ch149–161 的 80 MHz 块）只有主路由一台 80 MHz**，两个频段零重叠。
- **把 160 MHz 这块稀缺资源留给 AP**，因为 AP 侧扛着实际带宽需求：`bernard_5G` 上有主力 PC（`68:3e:26:0d:d0:22`，-33 dBm，当前 PHY 2401 Mbps）。降主路由不影响它。
- **把主路由挪到 ch149/80**，因为主路由 5G 只有 1 个客户端（`f2:8f:50:45:16:81`，-78 dBm，本身就贴边），80 MHz 绰绰有余；而且 ch149–161 是 CN 非 DFS、全楼最干净（1 个 -87 dBm 邻居）、**无需 CAC/雷达静默**，是长期最省心的落点。
- **主路由 5G 那 1 台客户端不会因此失联**：SSID/密码与 AP 的 `bernard_5G` 完全一致（同 SSID 漫游），它可以直接漫游到 AP 的 ch36/160 BSSID 上；即便不漫游，80 MHz 也能维持。
- **ch149/HE80 是主路由在本机上历史验证过的配置**（现网文档记录该机曾以 `bernard_5G` ch149/HE80 正常运行），回退目标明确，风险可控。
- 顺带：AP 的 `wl5`（隐藏 MiMesh，**当前 0 客户端**）会跟着 PHY 一起留在 ch36/160 —— 它仍在同块发射，但只剩**一路** 160 竞争者（原来两路），已消除「双 160 同块」的二次信道碰撞。若要彻底关掉它，**只能走小米 App 的 Mesh 开关**，**绝不要**动 UCI 的 `bh_ap_2g/5g.disabled`（历史事故：会让 `wl0/wl1` 主 SSID 一起消失）。

**备选（若你反过来更看重主路由 5G 的 160，或不想动主路由）**
- 主路由保持 **ch36 / HE160**，AP 在小米 App 里改 **ch149 / 80MHz** → 同样零重叠。
- 代价：AP 侧 4 个 5G 客户端（**含主力 PC**）断一次，且 PC 的 PHY 从 2401M 降到 ~1200M（80 MHz MCS11 2SS）。
- 本次不推荐的理由：动主路由更简单（自助、不碰 App），且把 160 MHz 留给有宽带需求的 PC 更划算。

### 6.3 改动归属速查

| 改动 | 谁能改 | 命令/入口 | 备注 |
|---|---|---|---|
| 主路由 2.4G ch6 → ch11 | ✅ **自助** | `uci set wireless.ra.channel='11'` + 提交 + reload | 只动 2.4G，5G 不受影响 |
| 主路由 5G ch36/HE160 → ch149/HE80 | ✅ **自助** | `uci set wireless.rai.channel='149'` / `uci set wireless.rai.htmode='HE80'` | **必须同时确认 `wireless.rai.country='CN'`** |
| 主路由回滚 | ✅ 自助 | 见 §7 | |
| AP 2.4G / 5G 信道与宽度 | ⛔ **只能在小米 App 改** | 米家 App → BE6500 Pro → Wi-Fi 设置 | 手改 `/etc/config/wireless` **改不动宽度**（UCI 写的是 `HT80`，运行态是 160）；且 `wifi reload` 有把主 SSID 搞挂的历史 |
| AP 的 `bh_ap_2g/5g`（MiMesh 隐藏 SSID）开关 | ⛔ App（**不要动 UCI**） | App 内 Mesh 相关开关 | UCI `disabled` 已被验证会搞挂 `wifi reload` |
| AP 的 IP / 有线回程 | ❌ 不动 | — | AP 是**有线**接主路由，`.138` 是 AP 本机静态地址 |

### 6.4 待执行的命令（**本次未执行，仅供你确认后再手动执行**）

```sh

# 2.4G：ch6 -> ch11（宽度不变）
uci set wireless.ra.channel='11'
uci commit wireless

# 5G：ch36/HE160 -> ch149/HE80（另起一个时段做，别和上面同时）
```

## 7. 潜在收益 / 不改的代价

### 7.1 改了能改善什么

| 维度 | 现状 → 改后 | 说明 |
|---|---|---|
| **5G 吞吐** | 两个 160 MHz 同块 → 单个 160 MHz + 一个独立 80 MHz | 160 MHz 的 secondary 80 MHz 不做保护，双发必撞。改后 AP 的 `bernard_5G` 独占 5170–5330，PC 的 PHY 仍是 2401 Mbps，但**有效吞吐从「反复重传的一半左右」回到接近链路速率** |
| **5G 时延 / 重传** | `rai0` Tx fail PER 20.3 %、Rx CRC PER 46.1 % → 预期显著下降 | 驱动计数器可直接复核（`iwpriv rai0 stat`） |
| **2.4G 边缘设备存活率** | 主路由 ch6 被 AP 的 40 MHz 覆盖 75 % → 零重叠 | 最受益的是 `chunmi-microwave`（-83 dBm，MCS2/6 Mbps）这类边缘 IoT：不再被同频 40 MHz 载波反复撞击，掉线/重连会明显减少 |
| **2.4G 整体空气时间** | ch1–9 区间少一路 40 MHz 底噪 | AP 侧 11 个客户端整体受益（ch1 那 12 个邻居还在，但少了一条自家人为的 40 MHz 干扰） |
| **漫游质量** | 两个 5G BSSID 分处 149 与 36 | 同 SSID 不同信道漫游时必须重新关联（1–3 s 断连），但**消除了「同信道强 BSSID 把客户端粘住」**的问题；同时 `SGT-AL10` 的双 BSSID 在册（乒乓）现象也会被信道分离重新洗牌 |
| **长期稳定性** | 主路由 `noscan=1` 永不自动选道 | 手动规划后，未来邻居变多时仍需人工复评；建议每季度或大促后重扫一次 |

### 7.2 不改的代价（维持现状）

- **5G**：本楼最挤的 ch36 上叠着 **3 个 160 MHz 发射源**（主路由 `rai0` + AP `wl0` + AP `wl5`）。主力 PC 的无线链路长期在重传中运行，**实际吞吐很可能只有标称 2401 Mbps 的一半左右**，而且 p99 时延会明显抬高；AP 的隐藏 MiMesh 无线（当前 0 客户端）还在白白占用一路 160 MHz。
- **2.4G**：主路由的 ch6 泡在 AP 的 40 MHz 载波里，`ra0` 的 Rx CRC PER **54 %**、Tx fail PER **23 %**；最弱的微波炉（-83 dBm / MCS2）大概率反复重连甚至掉线 —— 这类设备的「Wi-Fi 时好时坏」多半来自这里。
- **机会成本**：CN 下 160 MHz 只有 ch36–64 一块干净频谱，**不主动分配就等于把唯一的 160 资源浪费在两台设备互相打架上**。
- **运维风险**：主路由 `noscan=1` 意味着它永远不会自救；邻居密度变化时，现状会持续恶化而无人察觉。

## 8. 风险与兜底

### 8.1 改主路由的风险

| 风险 | 说明 | 规避 |
|---|---|---|
| **2.4G 客户端断连** | `ra0` 的 4 台（扫地机 / 空气炸锅 / 微波炉 / SGT-AL10）断 5–15 s；IoT 的重连逻辑差，可能要 30–60 s，甚至需要断电重启 | 选在家中无人在用时做；断电重启 IoT 前先记下各自当前连的是谁 |
| **`wifi reload` 触发网络重载** | 本机 `/sbin/wifi` 的 `reload` = `ubus call network reload` + legacy up/down → **PPPoE 可能掉线重拨**（LAN/SSH 不受影响） | 远程操作时确认你有 LAN 侧通道（你现在就在 LAN 上）；避开正在开会/看视频的时段 |
| **`wifi reload` 掉 SSH** | 只在从 WAN 侧登录时才会；LAN 侧不会 | 确保从 192.168.31.x 内网操作 |
| **ch149 在 country≠CN 时 NO-IR** | 若有人把 `country` 改成 `00` 或 `US`，ch149 会被判 NO-IR → **5G 整体消失** | 改完立刻 `uci get wireless.rai.country` 复核为 `CN` |
| **改了 `disabled` 导致无线全灭** | `wireless.ra0.disabled=1` 会让该接口彻底停 | **绝对不要**动 `ra0/rai0.disabled` |
| **改两个频段同时做** | 全屋无线同时断 | **一次只改一个频段**，改完验证再动下一个 |

### 8.2 改小米 AP 的风险（本次推荐方案不需要动 AP；若要动则必读）

- ⛔ **不要用 UCI 设 `bh_ap_2g` / `bh_ap_5g` 的 `disabled`** —— 2026-10-19 已实测：会导致小米 stock `wifi reload` 失败、主 SSID `wl0/wl1` 一起消失。
- ⛔ **不要用 UCI 改 `htmode`** —— AP 的 UCI 里写的是 `HT80`，运行态却是 `160 MHz`；**手改 UCI 改不动宽度**，只会造成「配置文件说 80、实际 160」的错乱（现在就处于这种状态）。**信道/宽度必须走小米 App**。
- ⚠️ App 里改信道后，AP 会重建全部 VAP（`wl0/wl1/wl4/wl5/wl13`），**所有连在 AP 上的设备（2.4G 11 台 + 5G 4 台）会断一次**。
- ⚠️ App 里 5G 的可选信道受 `channel_block_list` 限制：**只有 36/40/44/48/149/153/157/161**；**160 MHz 只在 ch36 成立**（149–161 凑不出 160 块，App 里选 149 时 160 选项会自动变灰/失效）。
- ⚠️ AP 的 2.4G 若选 HT40，**primary 只能选 ch1 或 ch11**（2.4G 40 MHz 的配对是 1+5 或 7+11），且它会把 ch1–9 整段泼满 —— 选 ch1+40 与主路由 ch11+20 是本报告推荐的组合。

### 8.3 兜底 / 救回手段（按顺序）

**小米 AP（有线连主路由，`.138`）**
1. **有线永远在**：`br-lan = eth0.1 eth0.2 eth1.3 eth1.4`，AP 的 IP 是**本机静态 `192.168.31.138`**（不在主路由 DHCP 池里，不会被抢）。**即使 WiFi 全挂，`.138` 依然在线。**
2. WiFi 出问题 → 从 LAN 内任一台机器：
   - `telnet 192.168.31.138`（root / **admin**）→ 改回配置 → `wifi reload`
   - 或 `ssh 192.168.31.138`（22 端口开放）
   - 或浏览器打开 `http://192.168.31.138`（小米 Web 后台，含 Wi-Fi 设置页）
3. Shell 卡死 / reload 后网络不通 → **给 AP 断电重启**：配置在 `/etc/config/wireless` 里持久保存，重启后回到最后一次已知可用状态，**不会丢 IP**。
4. 彻底失联（有线也不通）→ 只能物理断电重启；小米 AP 的出厂恢复键一般不暴露在 Web 端，若走到这一步需要长按 reset 复位（复位后 `.138` 静态地址会恢复，但 App 配的其它项需重配）。

**主路由（192.168.31.1）**
1. WiFi 改坏 → **走有线**连主路由 LAN 口（`lan1`~`lan4` 在 `br-lan`，`192.168.31.x`），SSH 上去改回 UCI。
2. **回滚命令（逐条，只读备份建议先做）**：
   ```sh
   # 回滚 2.4G
   uci set wireless.ra.channel='6'
   # 回滚 5G
   uci set wireless.rai.channel='36'
   uci set wireless.rai.htmode='HE160'
   uci commit wireless
   wifi reload
   ```
3. **改前请把现状快照留在本地**（只读，不动路由器）：
   ```sh
   uci show wireless      # 复制到工作区存档
   ```
4. 万一 `wifi reload` 后无线完全没起来：`/sbin/wifi status` / `ubus call network.wireless status` 看 radio 是否 `up`；必要时 `ubus call network.wireless up '{"device":"rai"}'` 单拉 5G（不触碰 WAN）。

### 8.4 后续复查建议

- 改完后 10 分钟、24 小时各复核一次：`iwinfo ra0 info` / `iwinfo rai0 info`（信道+带宽）、`iwinfo ra0 assoclist`（客户端数与 RSSI）、`iwpriv ra0 stat` / `iwpriv rai0 stat`（Tx fail PER / Rx CRC PER 是否下降）。
- 每季度或邻居变动后，在小米 AP 侧重跑一次 `iwlist wl1 scan` / `iwlist wl0 scan` 复测频谱占用（主路由的 `get_site_survey` 信道列不可信，见 §0.3）。
