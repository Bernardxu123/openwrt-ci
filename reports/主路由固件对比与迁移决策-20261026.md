# 主路由固件对比与「要不要换刷」决策评估

> 日期：2026-10-26 ｜ 现场：CT（主路由，QWRT R26.10.21）vs CU（实验机，PonWrt `r0-da111d3` + dae）
> 方法：两台机现场只读采集 + 工作区既有证据（`光猫-CT-HG5585F/` 取证、`reports/` 优化记录）
> 结论只对本工作区这两台机器负责；换刷决策请连同 §6 的风险清单一起看。

---

## 0. 一句话结论

**现在不建议把主路由（CT）换刷成我们编的固件。**
理由不是"我们的固件差"，而是：**换刷的收益（UDP 代理、省 50MB 内存）现在并不紧迫，而代价是把家里唯一的 PON+PPPoE 链路交给一套"在这台 CT 上从未实机跑过"的内核栈去重新自证**。
建议路径：**先恢复主路由 OpenClash（今天就要做，见 §5），让 dae 在 CU 上跑 3–7 天拿数据；同期完成两项零风险预验证（WiFi A/B、迁移清单）；再决定"刷 CT"还是"桥接+PPPoE 搬到 CU"**（§7 三方案对比）。

## 1. 两台机器是什么关系

同一块 PCB（AN7581 + MT7916 + 同一 UBI/factory 布局），**唯一实质差异是 lan1 的接法**：

| 项 | CT（电信版，现主路由） | CU（联通版，实验机） |
|---|---|---|
| SoC / 内存 | AN7581 / 512 MiB（内核可见 400 MiB） | 同（内核可见 422 MiB） |
| lan1 | **外置 MaxLinear GPY211C 2.5G**（2500base-x，GPIO34 复位） | 内建 PHY，**1G** |
| lan2–4 | 3×1G 内建 PHY | 4×1G 内建 PHY（含 lan1） |
| 无线 | MT7916（2.4G/5G 双频） | 同 |
| PON | Airoha XPON + paged BOSA | 同 |
| factory 卷布局 | calibration 2K / eeprom 4K / mac / pon-serial / device-serial | **完全相同** |
| 引导三件套（firstblock/preloader/fip） | 与 CU **逐字节不同** | — |

**现场事实（2026-10-26 15:2x 采集）**：

| | CT | CU |
|---|---|---|
| 固件 | QWRT `R26.10.21`（OpenWrt 25.12.3 基座 + **vendor 5.4.302** 内核） | PonWrt `r0-da111d3`（ImmortalWrt 25.12 基座 + **6.18.55**） |
| 角色 | **生产**：PON 注册 + `pon0.995` PPPoE（WAN `100.66.213.83`）+ NAT + 代理 + 无线 | 实验：`lan1` DHCP 从 CT 取 `192.168.31.250`，LAN `192.168.1.1`，dae 在跑 |
| 运行时长 | 4 天 19 小时（PPPoE 连接 4.3 天，`mpcp_timeouts` 累计仅 4） | 11 分钟（今天 15:0x 重启过） |
| 网口实际 | **只有 lan1@2500 有链路**（接小米 AP），lan2/3/4 空 | lan1→CT(1G)、lan2→PC(1G) |
| 无线 | vendor `mtwifi` 栈：2.4G ch11/HE20/24dBm + 5G ch149/HE80/25dBm，`psk2`，2 个客户端；另有 4 个备用 VAP 与 client-mode 接口 | 主线 `mt76`+hostapd 栈，今天关闭前仅验证"能起 AP"（20dBm） |
| 温度 | 68.8 °C（带无线+代理+2.5G） | 56.3 °C（无线关、负载低） |
| 代理 | OpenClash 0.48.002 + mihomo（**今天按你要求已关**，`enable=0`，无进程） | dae 2026.10.18，RSS 52–58 MB |

> ⚠️ 注意：CT 的 **lan1 是家里唯一的有线出口**（AP 挂在上面）。换固件后如果 2.5G 口起不来，**验证方式是把 AP 网线插到 lan2**（1G），一分钟可绕过——这点让"2.5G 未验证"从致命降级为可接受。

## 3. 换上我们的固件：得到什么

1. **UDP 出国能代理**（dae 的核心增量；QWRT 内核缺 nft_tproxy，mihomo 只能 fake-IP+TUN，UDP 受限）。
2. **内存 -50MB 级**（mihomo 105–125MB → dae 52–58MB），410MB 机器上余量从 ~100MB 升到 ~170MB，去掉历史 OOM 隐患。
3. **架构简化**：无 fake-IP、无 `2001:2::/64` hack、无双 nft guard 脚本、无 Ruby 层；一台设备一套配置。
4. **内核 6.18 + BTF**：可跑 dae 及一切 eBPF 工具（bpftrace/观测），未来可玩性/可排障性提升。
5. **可复现自建 + keep 制度**：以后固件是我们自己的 CI 出，改一行就重编；`/etc/dae`、`/root/dae-bak` 已进 keep。
6. **包管理可用**（apk + ImmortalWrt 源），需要 DDNS 等可现装，不再受 opkg 404 卡死。

## 4. 换上我们的固件：付出什么

1. **CT 硬件三处未验**（按风险排序）：
   - **2.5G 口**：包内 PR#34 已修（PHY ID 固定），真机未验；失败可临时改插 lan2（1G）绕过。
   - **WiFi 栈换血**：vendor mtwifi → 主线 mt76 + hostapd。CU 上只验过"能起 AP"；**穿墙、MU-MIMO/多客户端、长稳未验**。家里 WiFi 是刚需，这是最大不确定项。
   - **PON 长跑**：ponwrt 在 CU 上注册成功过（10-19），但 issue #42 的冷启动自循环与 `pon-watchdog` 的"半死"失败模式都真实存在。
2. **失去 QWRT 自带功能**：DDNS（在用！）、UPnP、Samba、IPTV(msd_lite)、vlmcsd、vsftpd、客户端历史、autoreboot。多数可另装/不需要，但 **DDNS 要补**。
3. **代理栈要重做**：OpenClash 的 19 组/规则 → dae（PC 侧已验证可行，但订阅（Clash YAML）需转换，机场节点未迁；目前只有自建 2 节点）。
4. **hw=0 保守值**：直连流量失去 PPE 硬卸载；1Gbps 家宽下软件 flowtable 大概率够，但**没有 A/B 数据**。
5. **风险叠加**：一次换刷 = 固件 + 代理栈 + 无线栈 + PON 四件事同时变；出问题时定位面大，且家里断网。
6. **镜像未签名**、dae 变体镜像今天才第一次真跑，**没有 24–72h 数据**。

## 7. 三条路线对比

### 路线 A：保持现在的双机结构（不改主路由固件）
- **A1 现状 + 恢复 OpenClash**：CT 继续 QWRT+OpenClash 服务全屋，CU 上 dae 只做实验/PC 加速。
- **A2 CU 当二级代理网关**：CU 变全屋网关，CT 降为 PPPoE 网关；**但**要不改线就让家用设备走 CU，需要把 AP/设备搬到 CU 后面（重新布线、CU 的 4×1G 取代 2.5G 干线），且 CT 的无线会落在代理之外（等于放弃 CT 无线）→ 复杂度高。

### 路线 B：CT 保留 PON，**桥接 + PPPoE 搬到 CU**（不刷 CT）
- CT 只做 ONT：`pon0.995 + lan4` 单独桥成 br-wan，其他口/无线成 br-lan；CU 在 lan1 上拨 PPPoE（拿到公网 IP，**无双 NAT**），成为全屋网关（dae、DHCP、静态租约都在 CU）。
- 优点：**不碰任何固件**，QWRT 的 vendor PON 栈不动；回滚= 改回 CT 两行配置。缺点：双线缆（PON→CU、CT-LAN→CU-LAN）、CT 变 AP/交换机、CU 4×1G 取代 2.5G 干线、网段要重编。工作量≈一次维护窗口。

### 路线 C：把 CT 刷成 PonWrt + dae（单机方案）
- 一台设备同时有 PON/PPPoE/2.5G/WiFi/dae，配置最简、长期可维护性最好。
- 代价：一次维护窗口 + §6 的 1/2/3 三条未验证项；任一硬伤 → 回刷 QWRT。

| 维度 | A1（现状） | B（桥接+PPPoE 到 CU） | C（刷 CT） |
|---|---|---|---|
| 改动面 | 0 | CT 网络配置 + CU 拨号/网段 + 布线 | 固件 + 配置 + 布线 |
| 断网窗口 | 0 | 1–2 h（可回退快） | 2–4 h（含验证） |
| 失败代价 | — | 低（改回配置即可） | 中（需重刷/救砖） |
| 全屋走 dae | ❌ | ✅ | ✅ |
| 保留 2.5G 干线 | ✅ | ❌（降到 1G） | ✅ |
| 保留 CT 无线 | ✅ | ✅（作为 AP） | ✅（换 mt76 栈） |
| 保留 PON vendor 栈 | ✅ | ✅ | ❌（换 ponwrt 栈） |
| 长期维护性 | 差（闭源+opkg 冻结） | 中（两机协作） | **最好** |

## 8. 如果决定走 C（刷 CT）：前置清单

**刷前（现在就能做，零风险）**
1. 恢复 CT 的 OpenClash + 把 `192.168.31.250` 加直连（§5①），保证过渡期家里正常。
2. 让 dae 在 CU 上连跑 3–7 天（`/root/dae-mon.log` 已装 cron 5 分钟），记录 RSS 曲线、断流、UDP 实际用例。
3. **在 CU 上做 mt76 WiFi A/B**：同硬件同位置，把 CU 无线开成 `bernard/bernard_5G` 同 SSID/PSK/信道，对比 CT 现网 vendor 栈的速率/信号；这直接回答 §6-3。
4. 准备最新 `dae` 版 **`-ct`** 镜像（CI dispatch `proxy=dae`），校验 sha256；同时备好 QWRT `R26.10.21 -ct` 回滚 itb。
5. 导出迁移清单（我能直接从 CT 读出来生成脚本）：
   `pon`（LOID/OAM/ge_ports）、`network.wan`（PPPoE 账号）、`wireless`（SSID/PSK/信道/country）、`dhcp` 静态租约 23 条、`/etc/dae/*`（CU 现版，`wan_interface` 改 `pppoe-wan`）、keep 列表、DDNS 配置。
6. 演练 U-Boot recovery（LAN2/3/4 + `192.168.0.1`），确认手上有一条能进 recovery 的路径。

**刷机窗口（2–4h，建议周末白天）验收门（按序，任一失败≥2 次即回滚）**
1. 起得来 + `192.168.31.1` 可管理；2. PON `lifecycle=operational` + `service_ready=1`；3. PPPoE 拿到 IPv4/v6；4. lan1 起 2.5G（失败→AP 改插 lan2 先保通）；5. WiFi 双频出 `bernard*` 且 PC 能连；6. dae 起、节点 ALIVE、`--interface` 测试出口=节点；7. 静态租约/DDNS 迁移完毕。

## 9. 建议（一句话版）

1. **今天**：恢复 CT 的 OpenClash + 给 CU 的 WAN IP 开直连，别让家里长期无代理。
2. **本周**：dae 在 CU 上跑 3–7 天 + 做 mt76 WiFi A/B + 我出迁移清单/转换器。
3. **之后二选一**：
   - 想要"最省事的长期形态"→ 走 **C（刷 CT）**，但必须接受一次维护窗口；
   - 想"零固件风险"→ 走 **B（桥接+PPPoE 搬到 CU）**，接受降到 1G 干线与一次布线；
   - 数据不好 / 不想折腾 → 停在 **A1**（QWRT 主路由 + OpenClash，CU 上 dae 仅实验）。
