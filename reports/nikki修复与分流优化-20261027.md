## 零、【最终结论 / 2026-10-27 15:55 补充】600M 的真凶 = **硬件流量卸载（`flow_offloading_hw=1`）**

> ⚠️ 本节推翻本文 §二 原先「600M 是测速站容量」的判断。用户手工关掉「路由/NAT 卸载 + 硬件流量卸载」后
> 报「正常了」，据此做了受控 A/B（同一目标 `mirrors.bfsu.edu.cn` 10 条流、同一时间段、背靠背连测 4 轮）：

| 状态 | 4 轮实测 (Mbps) | 中位 | 峰值 |
|---|---|---|---|
| 硬件卸载 ON（`flow_offloading=1` + `flow_offloading_hw=1`）← **原状态** | 729 / 640 / 618 / 665 | **640** | 729 |
| 全部关闭（`flow_offloading=0`）← 用户手工改的 | 891 / 917 / 840 / 845 | **845** | 917 |
| **只开软件卸载**（`flow_offloading=1` + `flow_offloading_hw=0`）← **最终采用** | 907 / 926 / 914 / 926 | **914** | 926 |

多源聚合复核（6 站点 ×3 流）：**984 Mbps** —— 已经是千兆线速（PPPoE 开销后）。

### 机制（flowtable 设备列表直接暴露）

```
hw=1 → flowtable ft { devices = { "lan1","lan2","lan3","lan4","pon0","ra0","rai0" }  flags offload }
hw=0 → flowtable ft { devices = { "br-lan","pon0.995","pppoe-wan" }                    }
```

`flow_offloading_hw=1` 时 fw4 会挑**硬件可卸载的物理设备**（`pon0`），而本机 WAN 是
**`pppoe-wan`（PPPoE over `pon0.995` over `pon0`）**——硬件 fast-path 的入口/出口设备对不上，
流量拿到一条"半残"的卸载路径：既不真正加速，又比纯软件转发更慢。
`hw=0` 时 fw4 用**逻辑接口**（`br-lan` / `pon0.995` / `pppoe-wan`），软件 flow offload 正常工作。

### 结论与配置

- **`flow_offloading_hw` 在本平台（AN7581 + PPPoE）必须关**，它是 600M 上限的直接原因。
- **`flow_offloading`（软件卸载）建议开**：比全关更快（914 vs 845）且省 CPU。
  实测软件卸载饱和 903 Mbps 时 CPU 仅 **≈29%**（4 核，softirq 为主）。
- 这与 AGENTS.md 里旧 LibWrt 时代「不要开 flow_offloading_hw」的记录一致，本次在 ponwrt 上给出了硬数字。

> 教训：之前把 600M 归因于"测速站容量/单流上限"是**错的**。多源并发能到 640–780 只是因为
> 硬件卸载对不同 flow 的劣化程度不同，把真实上限掩盖了。判据应该先做 offload 的 A/B。

## 一、GOMEMLIMIT 保存报错（已根因定位并修复）

### 根因

| 环节 | 事实 |
|---|---|
| uci 值 | `/etc/config/nikki:21  option env_go_mem_limit '80MiB'` |
| 页面定义 | `/www/luci-static/resources/view/nikki/app.js`：`o=s.taboption('environment_variable',form.Value,'env_go_mem_limit','GOMEMLIMIT');o.datatype='uinteger'` |
| 校验实现 | `/www/luci-static/resources/validation.js:46`：`uinteger(){return this.assert(this.factory.parseInteger(this.value)>=0,_('positive integer value'))}` |
| 结果 | `parseInteger('80MiB')` = NaN → 校验失败 → 报「正整数值」 |

关键影响面：该字段属于 `form.Map('nikki')`，**Map 级校验任一字段失败即整体拒存**。所以不只是改 GOMEMLIMIT 存不了，
**关 nikki（`nikki.config.enabled`）也存不了** —— 这就是用户遇到的现象。

`80MiB` 是合法的 Go 内存单位写法（mihomo 能正常用），错的是 luci-app-nikki 把这个字段声明成 `uinteger`，
两者不兼容。属于上游 luci-app-nikki 的 bug。

### 两个必须知道的坑（实测）

| 写法 | 结果 |
|---|---|
| `GOMEMLIMIT=`（空） | ✅ 正常，Go 视为「不限制」（`mihomo -t` exit 0） |
| `GOMEMLIMIT=80MiB` | ✅ 正常（但 LuCI 存不进去） |
| `GOMEMLIMIT=150`（纯数字） | ⚠️ 被当成 **150 字节**，Go 会疯狂 GC，mihomo 基本不可用。**而 `uinteger` 恰好只放行这种写法** |
| `GOMEMLIMIT=bogus` | ❌ 直接 runtime panic（实测崩溃，`mihomo -t` 出 goroutine dump） |

→ 结论：这个字段的正确用法是**永远留空**。要设限只能用 SSH 写带单位的值，且之后 LuCI 保存会再次报错。

### 修复动作

```sh
uci delete nikki.procd.env_go_mem_limit
uci commit nikki
```

`/etc/init.d/nikki` 用 `config_get` 取值，选项缺失 → 空串 → `procd_append_param env GOMEMLIMIT=""` →
进程环境里 `GOMEMLIMIT=`（空），Go 按「未设置」处理。

### 为什么这是性能修复，不只是一个 bugfix

修复前 `GOMEMLIMIT=80MiB` 而 mihomo 实际 RSS **95.4MB / VmHWM 108.4MB**，即**软上限长期低于活动堆**，
Go runtime 会持续贴着上限做 GC。修复后（同一配置、重启 3 分钟内）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| VmRSS | 95392 kB | 85976 → 89660 kB |
| VmHWM | 108356 kB | 91812 kB |
| MemAvailable | 104504 kB | 110024–113192 kB |
| core.log warning | 120+ 条 | 2 条（重启后累计） |

即：去掉上限后 RSS **反而更低**（不再被 GC 抖动抬高），可用内存 +6～9MB。

## 二、speedtest.cn 只有 600M：判定不是 nikki

### 2.1 证明测速流量根本不进 nikki

```
www.speedtest.cn   → 140.207.247.169   ∈ @china_ip (140.206.0.0/15)
file2.speedtest.cn → 211.95.51.x       ∈ @china_ip (211.80.0.0/12)
nodes-api / api-v3 / b / tisu-api / plugin → 均为国内 IP
```
nft `tablet inet nikki` 的 `nat_output` / `mangle_prerouting_lan` / `dstnat` 三条链里，
`ip daddr @china_ip counter return` 都排在 `jump ..._redirect` **之前** → 命中即 return，不进 mihomo。

旁证：
- 跑测速时 `@china_ip` return 计数持续增长（68452 → 68505）
- 同时刻 mihomo `/connections` 里 **0 条** speedtest 相关连接
- `/proc/net/nf_conntrack` 里没有 speedtest 流

**→ 关闭 nikki 对 speedtest.cn 的数字不会有任何改变。**

### 2.2 排除路由器 CPU / 线路

| 观测项 | 实测 |
|---|---|
| 600 Mbps 饱和时 CPU | 4 核总忙 **34.9%**（cpu0 40.6 / cpu1 26.7 / cpu2 34.7 / cpu3 37.3），未打满 |
| flow offload | conntrack `[OFFLOAD]` 计数 58 → 108 递增，已生效 |
| PPPoE 接口 | 错包 0 / 丢包 0，MTU 1492，MSS clamp 1452 |
| TCP 栈 | BBR + fq_codel（默认 qdisc） |
| PON 光路 | `rx_crc_errors 0`、`uncorrected_codewords 0`、`fec_error_seconds 0`、`mac_errors 0` |
| LAN | lan1 协商 2500，PC 网卡 1 Gbps，`ReceivedPacketErrors 0` |

### 2.3 多源并发实测（PC 有线，同一时刻）

| 测法 | 结果 |
|---|---|
| 8 个不同站点各 1 条流 | **780 Mbps**（另一次 642 / 673） |
| 16–24 条流压在 5–8 个站点 | 584 / 591 / 598 / 605 / 634 / 638 / 661 / 682 |
| 单站点 10 条流 | nju 683 / sustech 598 / tuna(8 流) 369 |

### 2.4 结论（**已被 §0 推翻，保留过程记录**）

> ❗ **实际根因是硬件流量卸载（`flow_offloading_hw=1`）把下行压在 ~640 Mbps**，详见 §0。
> 当时得出"站点容量"结论是因为没有对 offload 做 A/B：硬件卸载对多源并发流量的劣化程度不一致，
> 恰好把上限伪装成了 600–780。**判据修正：遇到「千兆线路只能跑 ~600」先做 offload A/B，再看测速站。**

原始观测（仍然成立）：600M 是**测速站点单节点/单会话容量**与**单流 TCP 上限**共同造成的，不是 nikki。
本线路用多源并发可稳定跑到 640–780 Mbps。想验证真实带宽必须换测法：
6–10 个国内镜像各 1–2 条流跑 15 秒，或改用「全球网测 / 中科大 test.ustc.edu.cn / 联通官方测速」。

> 顺带记录：speedtest.cn 的 `https://test.ustc.edu.cn/backend/garbage.php` 返回 500、IPv6 `test6.ustc.edu.cn` 也是 500，
> 这两个下载接口当前不可用，不要拿它当基线。

## 三、分流 / 内网修复（profile 4 处改动）

备份：`/root/bak-fix-20261027/{nikki.config,profile.yaml,run-config.yaml}`

### 3.1 内网设备名解析（本次最有价值的一处）

**症状**
```
tablet.lan   → NXDOMAIN
oppo_reno6   → 198.18.4.160   ← fake-IP，访问内网设备会被拽进代理
ct-hg5585f   → NXDOMAIN
（只有写在 /etc/hosts 里的 ap.lan / pc_eth.lan 正常）
```

**根因**：LAN 的 `:53` 在 `dstnat` 的 `lan_dns_hijack` 链里被直接 redirect 到 mihomo `:1053`，
**dnsmasq 被完全绕过**。mihomo 只通过 `use-hosts: true` 读 `/etc/hosts`，**不认识 dnsmasq 的 DHCP 租约**，
于是租约名要么落到上游 NXDOMAIN，要么按 `MATCH,fake-ip` 给个假 IP。

排查时有个陷阱：在路由器上跑 `nslookup tablet.lan 127.0.0.1` 也是 NXDOMAIN —— 因为 root 发起的查询同样被
`nat_output` 的 `router_dns_hijack` 劫到 1053，**看起来像 dnsmasq 不认识租约，其实是查询根本没到 dnsmasq**。

**修复**（nameserver-policy 新增）：
```yaml
  nameserver-policy:
    "+.lan":
      - 192.168.31.1
```
mihomo 查 `192.168.31.1:53` 不会回环 —— `nat_output` 首行就是
`socket cgroupv2 level 2 "services/nikki" counter return`，mihomo 自己的 DNS 出向被豁免。

**验证（PC 侧）**
```
tablet.lan      → 192.168.31.122   ✅
oppo_reno6.lan  → 192.168.31.198   ✅
ct-hg5585f.lan  → 192.168.31.1     ✅
pc_eth.lan      → 192.168.31.218   ✅
ap.lan          → 192.168.31.138   ✅
Ping ap.lan / pc_eth.lan / ct-hg5585f.lan 全通
```
`www.baidu.com` → 真实国内 IP、`www.google.com` → 198.18.0.21（fake-IP）——国内/国外分流未被破坏。

### 3.2 境外 DNS 反复失败的清理

**症状**（core.log 里 120+ 条 warning）
```
[TCP] dial 🐟 漏网之鱼 (match Match/) mihomo --> 8.8.4.4:853 error: ... connect error: context canceled
because ♻️ 香港自动 failed multiple times, activate health check
```

**根因**：`nameserver` 里的 `tls://8.8.4.4:853` 走规则 `MATCH → 🐟 漏网之鱼 → 🚀 默认代理 → ♻️ 香港自动`
（机场节点），该路径对 DoT:853 反复失败；失败还会连带把 `香港自动` 判成 failed 并**激活健康检查风暴**，
额外烧 CPU、拖慢境外解析。

**修复**：
```yaml
  nameserver:
    - https://1.1.1.1/dns-query
    - https://dns.google/dns-query      # 原来这里是 tls://8.8.4.4:853
```
保留两个上游做冗余，都走 DoH（HTTPS），不再用裸 DoT:853。

**验证**：重启后 warning 从 120+ 降到 2 条（其中一条是机场 `subscription-userinfo` 空值解析，与 DNS 无关），
`grep -i error core.log` **0 条**；`google generate_204` = 204 @0.74s、`youtube.com` = 200 @1.44s。

### 3.3 `GEOSITE,google-cn` 对齐为直连

```diff
- - GEOSITE,google-cn,🔍 Google
+ - GEOSITE,google-cn,🎯 直连
```
`google-cn` 系（`www.google.cn`/`gstatic.cn`）真实 IP 211.95.34.139 ∈ `@china_ip`（211.80.0.0/12），

旁证：`dl.google.com` 真实 IP 211.95.34.129 也在同一段。

### 3.4 测速站固定直连

```diff
+ # 测速站固定直连
+ - DOMAIN-SUFFIX,speedtest.cn,✈️ Speedtest
```
`✈️ Speedtest` 组当前选 DIRECT。作用是让测速流量在任何情况下（含 GeoIP 列表漂移）都是直连，
避免"测出来的是代理带宽"这类误判。

### 3.5 明确否决的一项（有数据）

原本打算给 `cn.download.nvidia.com` 加直连规则（它被 `zdgw.list` 的 `DOMAIN-SUFFIX,nvidia.com` 代理化）。
实测真实 IP：

