# 拨号 MTU 1500 评估（2026-10-26）

> 问题：`network.wan.mtu=1500`（PPPoE 拨号）是否最优？
> 方法：现网实测（`ssh_run.py`，2026-10-26 19:49–19:58）+ 路由器侧 tcpdump + PC 侧 DF ping + 配置/源码核对
> 测量时状态：主路由 HG5585F(ponwrt)，`pppoe-wan` up ≈75min，WAN `100.92.248.69`（CGNAT），代理栈为 **nikki/mihomo**（OpenClash 未运行）

---

## 0. 结论（TL;DR）

1. **`wan.mtu=1500` 是正确且已是最优的写法**。它的等价结果是 PPP 接口 `pppoe-wan = 1492`——这是标准 PPPoE 的硬上限（以太网 1500 − 8 字节 PPPoE 头），**不是**"设大了"。
2. 实测路径 MTU **精确等于 1492**：DF ping 1464B(总 1492) 通、1465B(总 1493) 被 `192.168.31.1` 回 ICMP `need to frag (mtu 1492)`、1472B(总 1500) 不通；IPv6 接口 MTU 同为 1492（1444B 总长 1492 实测可通）。MSS 实测 **1452**（=1492−40）。PMTUD 工作正常，无黑洞。
3. **不要把这个字段改回 1492**：本固件 netifd 会把 `wan.mtu` 同时写给父设备 `pon0.995` 和 pppd，写成 1492 会**二次扣 8 字节** → `pppoe-wan=1484` / MSS 1444（2026-10-22 审计已实测过，属倒退）。
4. 若目标是"PPP 接口真的是 1500"，只能靠 **RFC 4638 baby jumbo**（以太网 MTU 1508 端到端 + BRAS 协商 MRU 1500）。国内运营商普遍不支持；收益仅 8/1500 ≈ **0.53%**，失败代价是"声称 1500、实际 1492"的 PMTU 黑洞。**不建议在生产拨号上做**（受控实验步骤见 §6）。

## 1. 现网实测快照

### 1.1 接口 MTU

| 接口 | MTU | 说明 |
|---|---|---|
| `pon0` | 1500 | PON 物理口 |
| `pon0.995` | 1500 | VLAN 995（PPPoE 承载） |
| **`pppoe-wan`** | **1492** | **PPP 接口 = 实际 IP 路径 MTU** |
| `br-lan` / `lan1` / `ra0` / `rai0` | 1500 | LAN/无线，标准 |
| `omci0` | 1980 | PON OMCI 管理通道（与数据面无关） |
| `sit0` | 1480 | 6to4 默认值（未用） |
| `nikki`（代理 TUN） | 9000 | mihomo 默认 TUN MTU，与拨号无关（见 §5） |

### 1.2 配置与运行态

```
network.wan.device='pon0.995'  proto='pppoe'
network.wan.mtu='1500'  network.wan.mru='1500'  keepalive='5 5'

pppd 实参：... mtu 1500 mru 1500 plugin pppoe.so nic-pon0.995
```

- 即：**UCI/pppd 收的是 1500（ETH 侧），PPP 接口落 1492**。这 8 字节就是 PPPoE 头（6B PPPoE + 2B PPP protocol）。
- `netifd` 的 `proto_pppoe_setup()` 里 `mtu="${mtu:-1492}"` 是缺省兜底；真正下发由 `ppp_generic_setup` 的 `${mtu:+mtu $mtu mru $mtu}` 完成（`/lib/netifd/proto/ppp.sh`）。
- `firewall.@zone[1].mtu_fix='1'` 已开 → fw4 双向 MSS clamp 在位：
  ```
  oifname "pppoe-wan" tcp flags & (fin|syn|rst) == syn tcp option maxseg size set rt mtu   # egress
  iifname "pppoe-wan" tcp flags & (fin|syn|rst) == syn tcp option maxseg size set rt mtu   # ingress
  ```
- sysctl：`tcp_mtu_probing=1`、`ip_no_pmtu_disc=0`、`route.mtu_expires=600`（PMTUD 开启且带黑洞兜底）。
- `pppoe-wan` 收发错误/丢弃计数均为 0；`Ip: FragCreates=2410` 为运行期 UDP 等正常分片量级。

### 1.3 DF（Path MTU）实测 —— PC(192.168.31.218) → 223.5.5.5

| ICMP 载荷 | IP 总长 | 结果 |
|---|---|---|
| 1464 | 1492 | ✅ 通（2/2，6ms） |
| 1465 | 1493 | ❌ `need to frag (mtu 1492)` |
| 1472 | 1500 | ❌ 同上 |

路由器 lan1 抓到的 ICMP（关键证据）：

```
192.168.31.1 > 192.168.31.218: ICMP 223.5.5.5 unreachable - need to frag (mtu 1492), length 556
    IP (tos 0x0, ttl 128, id 58252, offset 0, flags [DF], proto ICMP (1), length 1500)
    192.168.31.218 > 223.5.5.5: ICMP echo request, id 1, seq 126, length 1480
```

→ 路由器明确告诉客户端"下一跳 MTU = **1492**"，PMTUD 正常，不存在静默丢包。

IPv6：`pppoe-wan` 的 v6 MTU = 1492（`/proc/sys/net/ipv6/conf/pppoe-wan/mtu`）；PC → 2400:3200::1 载荷 1444（总 1492）实测可通。载荷 1445 时 PC 侧把包按 1440 分片后未收到回包（抓包可见两段 IPv6 fragment），**不作为边界判据**，v6 边界以接口 MTU=1492 为准。

### 1.4 MSS 实测（tcpdump on pppoe-wan）

```
100.92.248.69.38946 > 153.3.238.28.80: Flags [S], options [mss 1452,sackOK,...]
100.92.248.69.59152 > 103.216.136.165.443: Flags [S], options [mss 1452,...]
```

→ 出向 SYN 的 MSS 恒为 **1452 = 1492 − 40**，符合 PPPoE 标准；无需任何额外 clamp 规则。
（PC 侧 SYN 的 mss 1460 是 LAN 1500 的正常值；WAN 侧由路由 MTU/MSS clamp 收敛到 1452。）

## 2. 为什么"1500"是对的、"1492"反而错

这是 2026-10-22 审计里踩过的坑，结论已固化进现网：

```
wan.mtu=1492  →  pon0.995 = 1492（netifd 把它也写给父设备）
              →  pppd 收 mtu 1492
              →  PPPoE 层再扣 8 字节
              →  pppoe-wan = 1484   ← 标准应 1492
              →  MSS = 1484−40 = 1444 ← 标准应 1452
```

所以：
- `wan.mtu=1500` 的正确语义是"**以太网侧最大帧 1500**"，PPP 接口自然落 **1492**；
- 把 1492 填进这个字段等于"在 PPPoE 上再 PPPoE 一次"，每包少 8 字节（≈0.53%）且 MSS 非标；
- 当前 1500/1500 正是修正后的目标状态，**保持不动**。

---

## 3. 能否把 PPP 接口做到 1500？（RFC 4638）

标准 PPPoE（RFC 2516）：Ethernet payload 1500 → PPP payload **1492**。
要 PPP 1500，必须 **RFC 4638 "baby jumbo"**：以太网 MTU **1508**（帧 1522B + FCS），且**两端都支持**：

1. 本机：`pon0/pon0.995` 需 1508（PON 驱动能过 1522B 帧；`omci0=1980` 说明 PON 封装本身有能力）；
2. 链路：OLT/接入网需透传 1522B 帧；
3. 对端：联通 BRAS 需支持并协商 MRU 1500（LCP 不 Nak 回 1492）。

收益与风险：

| 项 | 数值 |
|---|---|
| 每包多带 | 8 字节 |
| 相对增益 | 8/1500 ≈ **0.53%**（1Gbps 理论上限≈5Mbps，实际受 pps/CPU 限制更小） |
| 失败模式 | 接口声称 1500、实际路径 1492 → 大包被 BRAS 丢 → PMTU 黑洞（TCP 可靠 `tcp_mtu_probing` 兜底，UDP/QUIC 直接坏） |
| 国内支持度 | 三家运营商 PPPoE 普遍只给 1492；未发现联通 CU 支持 RFC 4638 的证据（公开讨论见 V2EX 846483） |

**结论：不做。** 现网 1492 已是"不带 baby jumbo 时的最优值"。

## 4. 其它 MTU 相关项（均无需动作）

| 项 | 现状 | 判定 |
|---|---|---|
| LAN / 无线 | 1500 | 标准，正确 |
| PC 网卡 | 1500 | 正确；**不要**为了 PPPoE 把客户端改成 1492（LAN 段就是 1500，WAN 段由 MSS clamp/PMTUD 处理） |
| fw4 MSS clamp | 双向 `set rt mtu` | 正确，跟随路由 MTU 自动算 1452；**不要**再加规则或装 "MTU fixer" 脚本 |
| `tcp_mtu_probing` | 1 | 保持 |
| `wan.mru` | 1500 | 无害（只影响接收声明；BRAS 不会发 >1492 的 PPP 载荷） |
| `nikki` TUN | 9000 | mihomo 默认，未在 config 写 `mtu`；TCP 由两端 MSS 自限，UDP 大包有理论分片风险但现网无故障证据。按 10-24 结论**不动** |

## 5. 复现方法（含两个坑）

```sh
# 路由器
uci show network.wan | grep -E 'mtu|mru'
ip -o link show | grep -E 'pon0|pppoe-wan'
ps w | grep pppd | grep -v grep
nft list ruleset | grep -i maxseg
sysctl net.ipv4.tcp_mtu_probing net.ipv4.ip_no_pmtu_disc
cat /proc/sys/net/ipv6/conf/pppoe-wan/mtu
```

```powershell
# PC（Windows ping 自带 DF；先清 PMTU 缓存）
netsh interface ipv4 delete destinationcache
ping -f -l 1464 223.5.5.5   # 总 1492，应通
ping -f -l 1465 223.5.5.5   # 总 1493，应回 "need to frag (mtu 1492)"
ping -f -l 1472 223.5.5.5   # 总 1500，应不通
```

**坑 1**：Windows 收到一次 PTB 后会缓存路径 MTU（约 10 分钟）。缓存后重复 `ping -f -l 1472` 会**本地直接**报 "frag needed" 且**不发包**（本次实测先出现该现象，清 `destinationcache` 后才重新看到路由器的 ICMP 1492）。
**坑 2**：busybox `ping` 无 `-M do`，路由器本机做不了 DF 探测；以 PC 侧 DF ping + `tcpdump` 为准。抓 SYN 用：
`tcpdump -i pppoe-wan -nn -v 'tcp[tcpflags] & tcp-syn != 0'`

## 6. 附：若一定要验证 RFC 4638（维护窗口，不建议日常做）

```sh
cp /etc/config/network /root/network.bak-$(date +%Y%m%d)
uci set network.wan.mtu='1508'
uci set network.wan.mru='1508'
uci commit network
ifup wan                       # 会短暂断拨（几秒~几十秒）
ip -o link show pppoe-wan | grep -o 'mtu [0-9]*'   # 期望 1500
# 从 PC：ping -f -l 1472 <公网 v4>，应通；同时 tcpdump 看 SYN mss 应为 1460
# 任一不符 → 立即回滚：
uci set network.wan.mtu='1500'; uci set network.wan.mru='1500'; uci commit network; ifup wan
```

判定标准：
- `pppoe-wan=1500` **且** PC DF 1472 通 **且** 无丢包 → 该线路支持 baby jumbo（可保留，但收益仍仅 0.5%）；
- `pppoe-wan=1500` 但 DF 1472 不通 → 最危险状态（接口与实际路径不一致），**必须回滚**；
- `pppoe-wan=1492` → BRAS 把 MRU Nak 回 1492，说明不支持，回滚。

## 7. 一句话给 AGENTS

> 拨号 MTU 保持 `network.wan.mtu/mru=1500`（→ `pppoe-wan` 1492 / MSS 1452）；**不要改成 1492**（会二次扣减成 1484）；**不要追 RFC 4638**（联通不支持、收益 0.53%、失败即 PMTU 黑洞）。验证用 PC 侧 `ping -f -l 1464/1465`（先清 `ipv4 destinationcache`）。
