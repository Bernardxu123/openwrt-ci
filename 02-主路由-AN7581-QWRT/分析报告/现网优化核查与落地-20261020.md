# 现网优化核查与落地（ponwrt / HG5585F-CU）

> **日期**：2026-10-20 21:20–22:20
> **目标机**：烽火 HG5585F-CU（AN7581，4×Cortex-A53 @ 500–1200MHz，438 MB RAM），PonWrt SNAPSHOT r0-e585ae8（kernel 6.18.55），主路由 `192.168.31.1`

## 0. 结论先行

前一版报告**大部分事实准确**（配置状态、PPE 状态、`packet_steering` 的作用、硬件卸载不绕过 tproxy 的判断全部为真），但**有两处技术性错误**，且两处错误恰好都把结论引向了"继续在绑核上加码"这个方向。

更重要的是：**本轮首次测出了这条线路的真实上限，而它证明 CPU 根本不是当前瓶颈。**

| 实测场景 | 吞吐 | 四核合计 busy |
|---|---|---|
| 有线 8 路并发直连下载 | **626–703 Mbps** | **~4%** |
| 代理路径（Cloudflare 经 xray） | 117 Mbps 单流 | ~56%（每核 ~14%） |

直连 670 Mbps 时四核只用了 4% —— 这是 **PPE 硬件卸载确实在工作**的铁证。CPU 在这个场景里完全没有压力。

**所以：本轮的改动不是"提速"，而是"削峰 + 补短板 + 防回退"。** 如果你的目标是"让网更快"，答案很可能是：现在这台机器已经不做瓶颈了，该查的是线路、代理节点、或客户端侧。

## 1. 对前一版报告的两处更正

### 1.1 ❌ 错误一：把 `smp_affinity_list` 当成位图来写

原文（`每核采样与IRQ归因报告` §3.3）写：

> | 23 (airoha_eth.0) | `8` (CPU3) | ❌ `Result not representable`（GICv3 该 SPI 的 target 寄存器受限） |
> | 54 (ethernet) | — | 同上类 |
>
> 结论：「irq 23 / irq 54 写不进去，不要浪费时间」

**实际原因是写错了格式。** `/proc/irq/N/smp_affinity` 用**十六进制位图**（`f` = 四核全开），而 `/proc/irq/N/smp_affinity_list` 用**十进制 CPU 编号列表**。往 `smp_affinity_list` 写 `8` 等于"我要 CPU8"，这颗 SoC 只有 CPU0–3，内核自然回 `-ERANGE`（`Result not representable`）。

**本轮实测（逐个 CPU 试，写后读 `effective_affinity_list` 确认）：**

```
irq 19 (mt7915e-hif INTx)  → CPU1/2/3 全部 Operation not permitted   ← 确实不可写
irq 23 (airoha_eth.0)      → CPU1 OK(eff=1) / CPU2 OK(eff=2) / CPU3 OK(eff=3)  ← 可写！
irq 27 (airoha_eth.4)      → 可写（原文这条试对了）
irq 53 (mt7915e MSI)       → EPERM                                   ← 确实不可写
```

写 `3` 而不是 `8`，irq 23 立刻就通了。

### 1.2 ❌ 错误二：把"两个 phy 共用一个 NAPI"误判成"5G 没绑上"

原文（§2.3(c)、§5-P1）写：

> CPU3 在 19–24 s 出现第二个尖峰…`wifi-napi-affinity` 把 2.4G 的 6 个 `napi/phy0-0` 线程钉在 CPU3；5G 的 `napi/phy1-0` 线程**没有对应条目**…所以 5G 的软中断/NAPI 落在哪由内核默认决定

**实际是同一个对象。** 本机 mt7915e 是**单芯片双频**：

```
phy0  MAC 00:0c:43:26:60:00   2.4G  bernard     ch6  HE20
phy1  MAC 82:0c:43:26:60:00   5G    bernard_5G  ch149 HE80
```

两个 MAC 同属 MediaTek（`0c:43`）前缀，共用 `0001:01:00.0` 这一个 PCIe 设备。mt76 的 NAPI 实例是**按 mt76 设备**创建的，名字取首个 phy，所以 6 个 `napi/phy0-N` 线程**同时服务 2.4G 和 5G**。

证据：全量扫 `/proc/*/comm`，`napi/*` 只有 `phy0-0`×6 和 `qdma_eth-0`×68，**不存在 `phy1-*`**；`mt76-tx` 也只有 `phy0` 一个。

**所以结论要反过来**：不是"5G 没绑上所以撞到 CPU3"，而是 **5G 和 2.4G 一起被绑在 CPU3，才导致 CPU3 冲到 83.7%**。原文建议的"补齐 5G 的 NAPI 绑核"无从下手（那个线程不存在），而真正的可选项是"是否把这 6 个线程分摊到多核"。

### 1.3 ✅ 原文正确且重要的部分

| 结论 | 复核 |
|---|---|
| `flow_offloading_hw=1` 只改了运行态未 commit | ✅ 属实（`uci changes` 有该条），本轮已 commit |
| 硬件卸载**不会**绕过 tproxy | ✅ 机制正确（tproxy 在 prerouting 截流并本地投递，被代理流永远进不了 forward flowtable），本轮实测代理出口 IP 不变亦可佐证 |
| `packet_steering=2` 把 NET_RX 分散开了 | ✅ 属实（IPI1 计数在 CPU1/2/3 显著） |
| `packet_steering.uc` 按 netdev 名匹配，对 airoha 失效 | ✅ 属实（NAPI 叫 `napi/qdma_eth-0`，netdev 叫 `pon0`） |
| 仓库 `99-hg5585f-setup` 有「检测到代理 → FLOW_HW=0」会打回 | ✅ 属实，本轮已改 |
| `packet_steering=2` 会把 WiFi NAPI 挪到 CPU0 | ✅ 属实 |
| `iwinfo assoclist` 的 MAC 是大写、统计要 `-i` | ✅ 属实的坑 |

## 2. 本轮实测数据（首次给出线路上限）

### 2.1 测试环境

- **PC 走有线千兆**（Realtek PCIe GbE，`192.168.31.106`，LinkSpeed 1 Gbps），**不是 WiFi**
  → 之前"手机 5G 测速 900 Mbps"的采样与用户当前主力机路径无关，不能混用
- 路由器自身流量**被 Passwall 代理**（`localhost_proxy=1`，出口 `155.254.108.53`）
  → **不能在路由器上 curl 测 WAN**，必须从 PC 侧测
- 测速源：清华 TUNA / 中科大镜像（直连）、Cloudflare `__down`（走代理）

### 2.2 直连（PPE 卸载路径）

3 轮 8 路并发，每轮 10 s：

```
第1轮  661 Mbps
第2轮  626 Mbps
第3轮  703 Mbps
```

**同时段每核 busy（8 路并发 670 Mbps）：**

```
cpu0=3%(峰6%)  cpu1=4%(峰10%)  cpu2=4%(峰12%)  cpu3=4%(峰9%)
四核合计 15% / 400%  → 利用率 4%
```

→ **PPE 卸载有效，CPU 完全不是瓶颈。** 这与前一版报告"CPU0 被打到 94%"并不矛盾：那是**WiFi 客户端**路径（mt76 无硬件 NAT，必须过 CPU 软栈），而**有线转发**走 PPE。两者是完全不同的场景。

### 2.3 代理路径（CPU 成本的真实来源）

12 次串行、每次 50 MB：

```
单流均值 117 Mbps
四核合计 56% / 400%（每核 ~14%）
xray 单核占用 ~10.7%（峰值 26%）
```

→ **代理的 CPU 成本约为直连的 14 倍。** 这才是这台机器上真正吃 CPU 的地方，也是唯一有优化空间的方向（但它受限于单流性能与节点，不是绑核能解决的）。

### 2.4 A/B：IRQ 迁移到底有没有用

同负载（8 路并发 20 s）、同线路、连续两阶段：

| 阶段 | IRQ 配置 | 吞吐 |
|---|---|---|
| A | irq23 + irq27 都在 CPU0（基线） | **678 Mbps** |
| B | irq27→CPU2, irq23→CPU1 | **673 Mbps** |

**结论：对峰值吞吐无影响。** 原因很清楚——负载只有 4% CPU，怎么摆都不影响。

> 过程中曾出现一次 B=388 Mbps，那是因为切换命令被 PowerShell 的 `$(...)` 吃掉、IRQ 实际没切过去，两阶段都是基线，388 只是线路波动。**这条线路的瞬时波动可达 ±75%，单次测量不足以判定任何结论。** 这是本轮最重要的方法论教训。

## 4. 明确的"不做"清单

| 项 | 为什么不做 |
|---|---|
| 继续加码绑核 / 拆分 WiFi NAPI 到多核 | 负载只有 4% CPU，边际收益为零；且 RPS 已在分发，强行绑核反而增加跨核 IPI |
| `gro_flush_timeout` / `napi_defer_hard_irqs` | 能减少硬中断次数，但会给每个包引入最多该值的额外延迟。当前硬中断率仅 ~1500/s，**不构成瓶颈**，没必要用延迟换 |
| CPU governor 改 `performance` | 当前 `ondemand` @850–950MHz（上限 1.2GHz）。4% 负载下满频只会多耗电多发热（现 54°C），无收益 |
| conntrack `max` 65535 | 当前 27648，实测用量 1605，**无压力** |
| zram 扩到 512 MB | MemAvailable 197 MB 仍宽裕，扩 zram 反而挤占 page cache |
| 移植 QWRT 的 `mt_whnat`（WiFi 硬件 NAT） | mt76 无此能力，闭源驱动才有，**不可移植** |

## 5. 如果还想更快，该往哪查

按可能性排序（都不是这台路由器能改的）：

1. **线路本身**。8 路并发 626–703 Mbps 且 CPU 只 4% —— 上限在联通侧或光路。单流 175 Mbps 是典型的单 TCP 流限制。
2. **代理节点/单流性能**。代理 117 Mbps、CPU 56%。瓶颈在 xray 单流 + 新加坡节点往返，不在本机。
3. **WiFi 客户端**。若用无线，瓶颈是 mt76 软栈（无硬件 NAT）+ 空口。实测 5G HE80 到 900 Mbps 已接近链路天花板。
4. **客户端侧**。PC 有线千兆，但单流只能到 175 Mbps，值得单独查（网卡驱动、TCP 窗口、目标站限速）。

## 7. 负面清单（本轮踩的坑）

1. **`smp_affinity_list` 是十进制 CPU 编号，`smp_affinity` 才是十六进制位图。** 写 `8` 想表达 CPU3 会得到 `Result not representable`。
2. **`ps w` 输出会被截断**，查线程全名要用 `cat /proc/<pid>/comm`。
3. **路由器自身流量被 Passwall 代理**（`localhost_proxy=1`），在路由器上 curl 测的是代理带宽，不是 WAN。
4. **单次测速不可信**：同一配置连续三轮 626/661/703，瞬时波动 ±75%。A/B 必须多轮、同负载、同时段。
5. **PowerShell 会吃掉 `$(...)`、`$`、`|`、`>`**：塞进 `python ssh_run.py "..."` 会被本地展开。一律 base64 管道上送：
   `echo '<base64>' | base64 -d > /tmp/x.sh && sh /tmp/x.sh`
6. **`ssh_run.py` 有 60 s 超时**，长测试要 `nohup` 后台跑再取结果。
7. **`Start-Process curl` 拿不到每流速度**，`curl --parallel` 在本机也返回 0；可靠做法是**串行多次**累加。
8. **`ubus call service delete` 报 Not found 不代表 enable 失败**，但它确实可能让第一次 `enable` 的软链没建上——检查 `ls /etc/rc.d/ | grep <svc>` 才作数。
9. **`pon0 rx_dropped` 一直在缓慢增长**（10 s +6，累计 69107，占收包 0.035%），量级很小，暂不处理；若日后追查 PON 侧丢包从这里入手。
