### A.2 结论

**没有过热、没有降频风险。**

- CPU 温度 51.5–51.7 °C，距 passive trip（95 °C）还有 **43 °C** 余量，距 critical（120 °C）还有 **68 °C** 余量。降频点远未触及。
- dmesg 全文无 `thermal`、`throttl`、`cpufreq: reducing` 类告警；`airoha-bsp-thermal` 校准正常（`BSP calibrated sensor: offset=22685 slope=5645`）。
- 唯一的"降频"现象是 `schedutil` 在低负载时**主动降频省电**（空闲时 4 核掉到 800 MHz），这是正常行为，不是热保护。

### A.3 风险

**真正的瓶颈不是温度，是 CPU 规格本身。**

- AN7581 的 CPU 是 **4 × Cortex-A53 @ 最高 1.2 GHz**。这是 2019 年级别的算力。
- 代理栈是 **Go 编写的 v2ray/xray**（VLESS + REALITY + xtls-rprx-vision），加密全部走软件：内核虽然加载了 `chacha20poly1305_neon` / `poly1305_neon` / `af_alg`，但 **v2ray 默认不走 AF_ALG**，仍用 Go 自带实现。
- 推算（**估算值，本次未做测速实测**）：单流代理吞吐大致落在 **100–300 Mbps** 区间，多流并发时 4 核 A53 会迅速见底。
- 5G 160 MHz 的 PHY 能力远超 1 Gbps，**因此"5G 160 MHz + 代理转发"这条链路上，瓶颈 100% 在代理的 CPU 侧，不在无线侧**。

### A.4 建议

| 优先级 | 动作 | 说明 |
|---|---|---|
| 高 | **把代理出站从软件加密切到硬件加速路径** | 若换用支持 AES-NI 等价指令的方案；ARMv8 `crypto` 扩展在 Go 里已用，但 1.2 GHz A53 的绝对算力仍是硬顶 |
| 高 | **降低代理链路的 CPU 成本** | 减少 mangle/规则命中数（当前 `ss_spec` 每包要查多个大 set：`china`/`blacklist`/`whitelist`/`music`/`gmlan`…），合并为单次 fib lookup |
| 中 | 考虑 `performance` governor | 当前负载下 `schedutil` 的动态调频会带来 500→1200 MHz 的抖动延迟，代理小包场景下改 `performance` 可降低 RTT 抖动（代价是功耗/温度） |
| 中 | **网卡 IRQ 亲和性** | 见 B.5——目前 100% 集中在 CPU0，是高包速率下的隐性瓶颈 |
| 低 | `tcp_congestion_control=bbr` | `tcp_available_congestion_control = reno cubic bbr`，**bbr 已可用但默认是 cubic**。路由器自身出站 TCP（到代理服务器）可用 bbr 改善 |

### B.2 结论：**硬件加速在 WAN 路径上实际上没有生效**

证据链是四条相互独立、方向一致的事实：

| # | 事实 | 推论 |
|---|---|---|
| 1 | `flow_offloading=1` + `flow_offloading_hw=1` → flowtable `ft` 已建、`flags offload` 已设、`flow add @ft` 规则已进 forward 链 | **配置层：已开启** |
| 2 | `an7581_bsp_ppe` 已加载，且持有 `nf_flow_table` / `nf_flow_table_inet` | **驱动层：PPE 已注册卸载回调** |
| 3 | flowtable 的 `devices` 列表 = `lan1,lan2,lan3,lan4,pon0,ra0,rai0`——**不含 `pppoe-wan`，也不含 `pon0.995`** | nft 的 `flow add` 要求**入/出设备都在 flowtable 里**。WAN 出口是 `pppoe-wan`（PPP 设备，本身也无法做硬件卸载），**因此转发到互联网的流永远加不进 flowtable** |
| 4 | 代理流量在 prerouting 被 NAT `redirect to :1234` | 被重定向到本地 socket 的流**在定义上就不可能被卸载**（流在用户态终止）。此外 `ip daddr @china return` 使国内流量直连，走正常 forward 路径，但出口仍是 `pppoe-wan`，同第 3 条 |

**补充观察：**

- **PPE 初始化降级**：`NPU PPE initialization command failed: -95` 后回退到 `legacy MT7916 PPE register initialization`。即这台 AN7581 跑的是 MT7916 时代的**兼容模式**（`engines 0x3`、2 个引擎），现代 NPU 路径不可用。这是固件层面的事实，不一定影响卸载能力，但说明 PPE 并未走"原生"路径。
- `bridge_offload=Y` + 持有 `br_netfilter` → PPE **可能**在做 **L2 桥接卸载**（WiFi↔有线 LAN 之间的二层转发），这条路径不依赖 nft flowtable。**但本固件不提供 PPE 计数器，无法证实**（`bridge_l2b_vids` 为空也暗示该项未配置）。
- `bridge-nf-call-iptables=0` → 桥内流量不经过 `ss_spec` 规则，代理只作用于 **IP 路由流量**。

### B.3 风险

- **低。** 卸载未生效不构成故障，只是"配置看起来开了、实际没开"的**认知陷阱**：容易让人以为"已经有硬件加速了，所以不用优化"。
- 卸载未生效 ⇒ **所有 WAN 流量都走 CPU**（这正是 A 节 CPU 天花板的直接原因）。
- 唯一的实际代价：forward 链每包多一次 flow-table 查找（实测总 CPU 5%，可忽略）。

### B.4 "关掉 flow_offloading 会不会有影响？"

**基本没有影响——因为它现在就是空转的。**

| 方面 | 关掉后 |
|---|---|
| 性能 | **无感知差异**。当前 forward 链里 `flow add @ft` 从未成功卸载任何流，关掉只是少一次查表 |
| 代理功能 | **无影响**。代理走 NAT redirect（用户态），与 flowtable 无关 |
| NAT / fullcone | **无影响**（`nft_fullcone` 独立） |
| 未来若 WAN 改成直连 IP（不经 PPPoE） | 关掉会**永久失去**该选项；但当前 WAN 是 PPPoE，改直连后 `pon0.995` 仍不在 flowtable 设备列表里，仍不会卸载 |
| 风险 | 极低。**唯一要留意的是 `flow_offloading_hw=1` + `fullcone` 的组合在部分内核上有交互**，但本机 flowtable 全程为空，无实际耦合 |

**建议：保持现状（`flow_offloading=1` / `flow_offloading_hw=1`）即可。** 关或开都不影响性能；关掉的唯一好处是"消除误解"，没有别的收益。**不要指望打开它能提速——它已经开着，而且没用。**

**真正值得做的是：** 若要榨干 AN7581 的硬件能力，方向不是 nft flowtable，而是 **PPE 本身的 L2 桥接卸载**（`bridge_offload`）与 **减少 CPU 侧每包工作量**。

### B.5 中断亲和性（额外发现）

```
/proc/interrupts:
  8:  62376670   0  0  0   1fb56000.ethernet      ← 100% 集中在 CPU0
```

- 开机至今 **6295 万次**网卡中断，其中 CPU0 占 **100%**；当前空闲负载下约 **1,151 次/秒**。
- `/proc/stat` 分核统计：cpu0 的 `irq` 计数是其余三核的 **10 倍以上**。
- **风险**：千兆线上 1500 字节包 ≈ 83,000 pps，若全部落到 CPU0，CPU0 会先饱和（`net.core.netdev_max_backlog=1000` 也不够用）。
- **建议**：启用 `irqbalance`，或把 `1fb56000.ethernet` 的 smp_affinity 分散到 4 核。

### C.2 结论

**PON 线路质量优秀，无丢包/无错误/无光功率异常迹象。**

- 零 FEC 误码、零 CRC 误码、零失步、零重协商、零光功率异常。
- 注册自开机起一次未断（4.28 h 全程 registered）。
- 唯一可挑的是**本地缓冲层面的少量丢包**：`pon0` RX dropped 24,413（0.074%）、`pppoe-wan` RX dropped 6,752（0.05%）、xpon 描述符丢 7,793（0.024%）。这些**不是线路误码**（FEC/CRC 全为 0），而是 QDMA 描述符/缓冲瞬时耗尽，属于高速率突发时的正常挤压。当前 10s 采样下 WAN 实际流量仅 ~2 Mbps，远未触压。

### C.3 风险

- **低。** 0.05–0.07% 的本地丢弃在当前流量下无感知。
- **一个值得留意的观察**：10 s 采样中 `pon0` RX ≈ **11.5 Mbps**，而 `pppoe-wan` RX 仅 ≈ **1.98 Mbps**。累计量上 `pon0` RX 40.96 GB vs `pon0.995` RX 14.07 GB——**约 2/3 的 PON 下行流量不在 VLAN 995 上**。
  - 最可能解释：联通 **IPTV 组播 / 其他 VLAN**（如 TR069 VLAN 28）在 pon0 上被接收但不路由进 PPPoE 会话。**这是正常的，不是故障**，但如果确认是 IPTV 组播，会长期占用 pon0 的 RX 描述符配额（0.024% 的描述符丢弃可能与此有关）。
  - 建议：向联通确认是否已开通 IPTV，以及组播 VLAN 号；若未开通，排查是否有非预期的 VLAN 下行流量。
- `mac_errors: 4` / `last_mac_error: 0x00000100`——全部对应开机 Discovery Gate 阶段的 `EPON MAC error interrupt: 0x0100`（dmesg 可见），属注册收敛期噪声。

### C.4 建议

| 优先级 | 动作 |
|---|---|
| 中 | 确认 IPTV/组播 VLAN 归属，评估 0.024% 描述符丢弃是否与之相关 |

### D.2 结论

**内存余量当前充足，但没有任何缓冲垫。**

- 182 MB MemAvailable / 45.5% 可用，slab 中 55.9 MB 不可回收（内核 + conntrack + nftables 大 set + 驱动），`Committed_AS` 仅占限额 60%——**当前状态健康**。
- **但 swap=0 且 zram 未启用**。在 400 MB 的机器上跑 Go 语言的 v2ray + nftables 大 set（`china` 集合有数千条 interval），一旦出现内存尖峰（v2ray 大流量时的 buffer 膨胀、内核 slab 增长、连接数暴涨），**没有 swap 就没有退路**，只能触发 OOM killer 随机杀进程（大概率杀掉 v2ray 或 dnsmasq）。

**关于"overlay 才 1% 有没有异常"——结论：完全正常，没有任何异常。**

理由：
1. `rootfs_data` 是 **dynamic UBI 卷，容量 199.5 MiB**，几乎占满整片 NAND 的剩余空间——这是刷机时按 NAND 容量自动划分的，**不是"你用得少所以小"**。
2. `/overlay` 显示的 182.4 MiB 是 UBIFS 扣除 9 MiB journal + 4.8 MiB root 保留后的可用值。
3. 1% 只是说明**这台机器刚刷完 QWRT不久、写入的文件还很少**（UCI 配置、日志、少量包）。根文件系统本体在只读的 `/rom`（squashfs 36 MB，100% 是常态）。
4. 擦除计数最大只有 2 → **NAND 几乎全新，磨损无忧**。

> ⚠️ 唯一与 overlay 相关的**真正风险**不是"1%"，而是 **UBIFS 9 MiB journal + NAND 磨损**：如果后续装大量包、或把日志/代理配置高频写入 `/overlay`（UBIFS 写放大明显），会加速 NAND 擦写。**日志与频繁变动文件应放 `/tmp`（tmpfs）**。

### D.3 建议

| 优先级 | 动作 | 说明 |
|---|---|---|
| **高** | **启用 zram（128–192 MB，priority 100）** | 400 MB 内存 + 无 swap 是真实尾部风险。`/etc/config/system` 已有 `zram_comp_algo`，启用 swap 服务即可；建议 `zram_size=192MiB`、算法改 `zstd`（lzo 压缩比更差但 CPU 更省，A53 上 zstd 开销偏大，**建议保留 lzo 或试 zstd**） |
| 中 | zram 场景下调 `vm.swappiness` | 建议 30（纯 zram 无磁盘 swap 时 30~100 都可，30 更保守） |
| 中 | 关注 `SUnreclaim`（当前 55.9 MB） | 不可回收 slab 已占 13.6% 内存，代理规则变动会推高它；变更 nft 集合后观察 |
| 中 | 代理日志/频繁写文件放 `/tmp` | 保护 NAND 磨损（UBIFS 写放大） |
| 低 | `fs.file-max = 40,946` 偏低 | 建议提到 65,536+；服务进程 `ulimit -n` 当前仅 **1024** |

**MTU 传导链（实测复现）：**

```
/etc/config/network:
    network.wan.device='pon0.995'
    network.wan.proto='pppoe'
    network.wan.mtu='1492'
    network.wan.mru='1492'

pppd 实参:
    pppd nodetach ... mtu 1492 mru 1492 plugin pppoe.so nic-pon0.995
                                    ↑ 与父设备 MTU 同为 1492

结果: pon0.995 = 1492  →  pppd 再扣 8 字节 PPPoE 头  →  pppoe-wan = 1484
```

```
}
chain mangle_forward {
    iifname "pppoe-wan" ... tcp option maxseg size set rt mtu comment "!fw4: Zone wan ... ingress MTU fixing"
```

- 路径有效 MTU = **1484**，比 PPPoE 标准值 1492 少 8 字节 → MSS 1444 而非 1452。
- 因为 fw4 用的是 `tcp option maxseg size set rt mtu`（跟随路由 MTU 动态计算），**只要把 MTU 改对，MSS 自动跟着变，不需要动任何 nft 规则**。
- **不会出现 PMTU 黑洞**：clamp 保证 SYN 里的 MSS 始终 ≤ 路径实际 MTU，路由器不会发出超出对端能力的报文。
- **conntrack 完全无压力**：65535 上限、当前 898–993（1.5%）、桶数 16,384 合理、SYN_SENT 仅 19 条。**不需要任何调整。**
- 时间戳观测：`SYN_SENT 19 / ESTABLISHED 126`（约 13%）略高于常规，但绝对值极小，**不构成问题**；可结合代理节点质量观察。

### E.3 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| 路径 MTU 1484 非标准 | 低-中 | 每包少 8 字节（~0.5% 效率损失）；更麻烦的是**非标准 MSS 可能与某些隧道/中间盒假设冲突**（如叠加 WireGuard/VPN 时 MTU 链更长） |
| `tcp_mtu_probing=0` | 中 | 万一某条路径真出现 PMTU 黑洞，无探测兜底 → 会表现为"个别网站卡住" |
| `core.rmem_max/wmem_max=208 KB` | **中** | TCP 自动调优被硬压到 208 KB/套接字，**这是代理单流吞吐的隐形天花板之一**（与 CPU 瓶颈叠加） |
| `netdev_max_backlog=1000` + `tcp_max_syn_backlog=128` | 中 | 突发/高包速率时丢包与 SYN 丢弃 |
| `nf_conntrack_acct=1` + `nf_conntrack_events=1` | 低 | 非默认，每包额外记账/事件开销，对 400 MB 机器的 CPU 有可测量的浪费 |
| `send_redirects=1` | 低 | 无收益 |
| 全部网卡 IRQ 集中在 CPU0 | 中 | 见 B.5 |

### E.4 建议

**MTU / MSS：**

1. **推荐改法（单变量、可回滚）**：`/etc/config/network` 里把 `network.wan.mtu` 与 `network.wan.mru` 从 `1492` 改为 **`1500`**（或直接删掉这两行让 OpenWrt 取默认 1500）。
   - 效果：`pon0.995` = 1500 → pppd 扣 8 字节 → `pppoe-wan` = **1492** → MSS **1452**（标准值）。
   - **nft 的 MSS clamp 规则不用动**，它会自动跟随。
   - 改动后需验证：`ping -M do -s 1472`（或大包 + DF）到外网，以及浏览/下载无异常。
2. **兜底**：同时设 `net.ipv4.tcp_mtu_probing=1`（ICMP 黑洞探测），这样即使有路径不支持 1500 也能自愈。
3. 若要更保守，也可保留现状（1484 能正常工作），只是失去 8 字节。

| `net.netfilter.nf_conntrack_events` | 1 → **0** | 去每包事件通知 |

**与既有文档的冲突（重要，需订正）：** AGENTS.md 记录 ONT 5G 为 **ch149 / 80MHz**，且"与 AP 5G ch36/160 不再重叠"。**实测当前 ONT 5G 已是 ch36 / HE160**（`wireless.rai.channel='36'`、`htmode='HE160'`），而小米 AP（BE6500 Pro）按文档仍在 **ch36 / 160MHz**——**两者现在完全同频同宽，正处于同频干扰状态**。这与 46% 的 CRC 误码率高度吻合（两台 AP 互相能听到对方的帧但无法协调）。

> 说明：CRC 误码也可能部分来自某个远端 STA 信号本身太弱（−78 dBm）。两个原因**可以同时成立**：同频冲突影响整体空口，弱 STA 拉低聚合统计。区分方法：把 ONT 5G 挪到无冲突信道后复测 `iwpriv rai0 stat` 的 `Rx with CRC` 增量。

2.4G 侧同样存在部分重叠：ONT = ch6/HE20，而小米 AP 2.4G 按文档是 ch1/HT40（覆盖 1–9）→ **信道 6 重叠**。

### F.3 建议

| 优先级 | 动作 | 预期 |
|---|---|---|
| **高** | **把 ONT 5G 从 ch36/HE160 挪开**（例如回到 ch149/HE80，或换到 149/160 的另一块 160MHz 连续块），解除与小米 AP 的同频冲突 | CRC 误码率应从 ~50% 大幅下降；这是当前 5G 吞吐的第一瓶颈 |
| 高 | 让小米 AP 5G 换到与 ONT 不重叠的信道/带宽（二选一即可，不要两边都改） | 同上 |
| 中 | 2.4G 错开：ONT ch6/HE20 vs AP ch1/HT40 → 任一侧改到不重叠信道 | 减少 2.4G 干扰 |
| 中 | 排查 RSSI −75~−78 dBm 的具体 STA 是谁（距离/遮挡/天线） | 弱 STA 会持续拉高聚合 PER |
| 低 | 排查 MT7916 驱动在 HE160 + `noscan=1` + `smart=1` 组合下的行为：`Current BW Tx count` 仅占 1.3%，与 `Last TX Rate=BW160` 自相矛盾 | 可能是驱动在 160 MHz 下并未真正以 160 发射 |
| 中 | 关注 5G 关联抖动（每 15–35 分钟一次 REASSOC） | 漫游/重连会打断长连接（视频、代理会话） |

## G. 六个问题的直接回答

### Q1：AN7581 在当前 QWRT 下硬件加速（PPE/NSS/HTNAT）到底有没有生效？关掉 flow_offloading 会不会有影响？

**没有生效——至少在 WAN（互联网）路径上确定没有生效。**

**证据（四条独立、互相印证）：**
1. **配置层是开的**：`flow_offloading=1` + `flow_offloading_hw=1`，nft flowtable `ft` 已建（`flags offload`），`flow add @ft` 规则已在 forward 链。
2. **驱动层是就位的**：`an7581_bsp_ppe` 已加载，且持有 `nf_flow_table` / `nf_flow_table_inet`（PPE 已注册卸载回调）；`nf_flow_table_hw` 虽加载但 holders 为空（PPE 走自有路径而非通用 `register_flow_offload` API）。
3. **结构性阻断**：flowtable 的设备列表是 `{lan1..lan4, pon0, ra0, rai0}`，**不含 `pppoe-wan`，也不含 `pon0.995`**；而默认路由出口正是 `pppoe-wan`（PPP 设备本身也不能做硬件卸载）。**⇒ 转发到互联网的流根本加不进 flowtable，软件/硬件卸载双双无从谈起。**
4. **代理流量在定义上不可卸载**：`inet ss_spec` 在 prerouting 用 `redirect to :1234` 把流量重定向到本地 v2ray，**在用户态终止的流永远不能被硬件卸载**。国内流量虽走正常 forward 路径，但出口仍是 `pppoe-wan`，同第 3 条。

**额外佐证**：PPE 初始化时 `NPU PPE initialization command failed: -95`，回退到 `legacy MT7916 PPE register initialization`——现代 NPU 路径不可用，跑的是 MT7916 兼容模式。

**局限声明**：本固件**未暴露任何 PPE 统计接口**（debugfs 只有 `airoha-xpon-pon0`，无 ppe 节点；`/proc` 下无 ppe 节点；dmesg 自报 `stats 0x0`），因此**无法直接读出"硬件卸载流计数器"**。以上结论是基于配置/驱动/路由/规则四层结构的**推断**，而非直接计数。唯一无法证实的是 **PPE 的 L2 桥接卸载**（`bridge_offload=Y` + 持有 `br_netfilter`）可能对 WiFi↔有线 LAN 的二层转发有加速，但同样缺乏计数器。

**关掉 flow_offloading 会不会有影响？→ 几乎不会，因为它现在就是空转的。**
- 性能：无感知差异（实测总 CPU 仅 5%，且从未卸载成功过任何流）。
- 代理：不受影响（走 NAT redirect，与 flowtable 无关）。
- NAT/fullcone：不受影响。
- **建议保持现状**。关掉的唯一收益是"消除"已经开了的误解；没有任何性能收益。不要指望打开它能提速——**它已经开着，而且没用**。

### Q2：CPU/温度有没有过热降频风险？5G 160 MHz + 代理转发的负载下会不会成为瓶颈

**过热/降频：完全没有风险。**
- 51.5–51.7 °C，距 passive trip 95 °C 尚有 43 °C，距 critical 120 °C 尚有 68 °C；dmesg 无任何 throttle 记录。
- `schedutil` 空闲时把 4 核降到 800 MHz 是省电行为，不是热保护。

**瓶颈：会，而且分两层。**
- **第一层（当前最痛）不是 CPU，是无线空口**：5G 射频 **46% 累计 / 51.6% 实时 CRC 误码率**、STA RSSI −75~−78 dBm、20% 发送失败率。物理层已经在丢一半的帧，**这一层的损失远大于 CPU**。根因高度疑似 ONT 5G(ch36/HE160) 与小米 AP 5G(ch36/160) **同频同宽冲突**（与 AGENTS.md 记载的"ch149/80 不重叠"已不符，需订正）。
- **第二层才是 CPU**：4×Cortex-A53 @ 1.2 GHz 上跑 Go 版 v2ray（VLESS+REALITY），加密全软件实现（未走 AF_ALG）。**估算代理吞吐上限约 100–300 Mbps**（估算值，本次未做测速）。5G 160 MHz 的 PHY 能力 >1 Gbps，**所以"5G 160 + 代理转发"这条链路上，CPU 是最后一道闸门但远不是当前的第一瓶颈**——先把空口修好。
- **第三层（隐性）**：`core.rmem_max/wmem_max=208 KB` 压住 TCP 自动调优、网卡 IRQ 100% 挤在 CPU0、`netdev_max_backlog=1000`。

### Q3：512 MB RAM / 256 MB NAND 的当前余量，是否需要加 zram/swap？当前 overlay 才 1% 有没有异常

**余量：** MemTotal 400.6 MB（物理 512 MB 扣掉内核保留），MemAvailable **182 MB（45.5%）**，used 156 MB，Committed_AS 124/205 MB。**当前健康。**

**是否需要 zram/swap：建议加（zram 128–192 MB，priority 100），因为目前是「0 swap + 0 zram」，没有任何缓冲垫。**
- 400 MB 内存 + Go 代理 + nftables 大 set + 55.9 MB 不可回收 slab，一次内存尖峰就只能靠 OOM killer（大概率杀掉 v2ray 或 dnsmasq）。
- `/etc/config/system` 已有 `zram_comp_algo='lzo'`（**但未启用**），`/etc/config/fstab` 显式 `anon_swap='0'`。**加上 zram 后建议 `vm.swappiness=30`。**
- 不建议用 NAND swapfile：UBIFS 写放大 + NAND 磨损（虽然现在擦除计数只有 2，几乎全新）。

**overlay 1% 有没有异常 → 完全没有异常，是正常现象。**
- `rootfs_data` 是 dynamic UBI 卷，**容量 199.5 MiB 是刷机时按 NAND 容量划分的**，不是"用得少所以小"；UBIFS 扣掉 9 MiB journal + 4.8 MiB root 保留后，`/overlay` 可用 182.4 MiB。
- 1% 只反映"刚刷机不久、写入文件还少"。根文件系统本体在只读 `/rom`（squashfs 36 MB，100% 是常态）。
- **NAND 状态极好**：Toshiba 256 MiB SLC，坏块仅 3 个，最大擦除计数 **2**（几乎全新）。
- 真正该关注的是 **UBIFS 的 9 MiB journal 与 NAND 磨损**：代理日志、频繁变动文件应放 `/tmp`（tmpfs 200 MB，已用 9.5 MB）。

### Q4：PON 线路有没有丢包/错误/光功率异常迹象

**没有。线路质量优秀。**
- **FEC：4.1 亿码字，`corrected_codewords=0`、`uncorrected_codewords=0`、`error_bytes=0`、`error_bits=0`、`fec_error_seconds=0`。**
- **失步 0 次（`sync_loss_count_hw=0`、`sync_losses=0`）、重协商 0 次（`recoveries=0`、`full_reinitializations=0`）、掉线 0 次。**
- **光功率 −16.99 dBm（优秀区间）、光模块 38.38 °C、偏置 9.85 mA、供电 3.20 V、校准 ready、error=0。**
- **注册稳定**：LLID 164 valid，`mpcp_state=registered`，自开机起 `registered_lifetime_ms ≈ 4.28 h` = uptime 全程未断；4 次 MPCP timeout + 1 次 deregister **全部发生在开机 27–38 s 的注册收敛期**，此后零复发。
- **OAM 在线**（oam0 UP，15,922 RX / 15,861 TX，0 错误）；omci0 DOWN 且 0 报文——联通用 OAM 不用 OMCI，**正常**。
- **仅有轻微本地丢弃**（非线路误码）：`pon0` rx_dropped 24,413（**0.074%**）、`pppoe-wan` rx_dropped 6,752（**0.050%**）、xpon 描述符丢 7,793（0.024%）。这是 QDMA 缓冲/描述符瞬时耗尽，当前 ~2 Mbps 流量下无感知。
- **一个待确认项**：10 s 采样中 pon0 RX ≈ 11.5 Mbps，而 pppoe-wan RX 仅 ≈ 1.98 Mbps；累计 pon0 RX 40.96 GB vs pon0.995 RX 14.07 GB。**约 2/3 的 PON 下行不在 VLAN 995 上**——最可能是**联通 IPTV 组播/其他 VLAN（如 TR069 VLAN 28）**。这不是故障，但建议向联通确认是否已开通 IPTV，以解释那 0.024% 的描述符丢弃。

### Q5：PPPoE/MTU/MSS 有没有需要 clamp 的地方

**MSS clamp 不需要新增——fw4 已经写好了**（`Zone wan IPv4/IPv6 egress/ingress MTU fixing`，用 `tcp option maxseg size set rt mtu` 动态跟随路由 MTU，方向正确、作用点正确）。

**但 MTU 基数被重复扣减，需要修正：**
- 实测：`pon0.995` = **1492**（来自 `network.wan.mtu='1492'`）→ pppd 实参 `mtu 1492 mru 1492` → 再扣 8 字节 PPPoE 头 → **`pppoe-wan` = 1484** → **MSS = 1444**（标准应为 1492 / 1452）。
- 即 1492 被扣了两次：用户配的 1492 语义本是"PPP 接口 MTU"，netifd 却同时下发给父 VLAN 设备和 pppd。
- **修正（单变量、可回滚）**：把 `/etc/config/network` 的 `network.wan.mtu` / `network.wan.mru` 从 `1492` 改成 **`1500`**（或删掉这两行走默认 1500）。效果：pon0.995 = 1500 → pppd 扣 8 → pppoe-wan = **1492** → MSS **1452**。**nft 的 clamp 规则不用动**，会自动跟随。改后需验证大包 DF 通过、外网浏览/下载正常。
- **兜底**：同时开 `net.ipv4.tcp_mtu_probing=1`，这样即便某条路径真的不支持 1500 也能自愈（当前是 0，等于没有 PMTU 黑洞保护）。
- 保留现状（1484）也能正常工作，代价只是每包少 8 字节 + 与叠加隧道时的兼容性隐患。
- 其他 MTU 均正常：`omci0` 1980（jumbo）、`sit0` 1480（6to4 标准值）、`br-lan`/lan*/ra*/rai* 1500。
- **代理侧的 MTU 天然自洽**：代理是"本地终止"（redirect），客户端↔路由器一段（LAN 1500/MSS 1460）、路由器↔代理服务器一段（WAN 1484/MSS 1444）各自独立协商，不会跨段失配。

## I. 审计方法与局限

**执行方式**：全部通过工作区 `ssh_run.py`（paramiko SSH）执行**只读命令**（`cat` / `ls` / `ip` / `nft list` / `sysctl` / `dmesg` / `logread` / `ubinfo` / `iwpriv` / `ethtool` / `free` / `df` / `mount`）。

**未做的事**（遵守"不改配置、不重启、不写文件"）：
- 未做任何 `uci set` / `uci commit` / `sysctl -w` / 文件写入 / 服务重启
- **未做测速**（因此代理吞吐上限是**估算值**，非实测）
- 未做压测/打流（因此 CPU 占用是**空闲态**数据，繁忙时会更低——注意这里的低占用是"当前负载低"，不是"性能好"）
- 未触碰 `/etc/config/pon` 的写操作；读取时对 LOID/凭据做了打码
- 未读取 PPPoE 明文密码、WiFi 密钥、代理凭据到报告中

**已做的只读采样**：
- CPU：10 s / 20 s 两个窗口的 `/proc/stat` 分核增量 + `/proc/<pid>/stat` 进程级增量
- 热区：5 次连续采样（2 s 间隔）
- 流量：2 个 10 s 窗口的接口字节计数增量
- WiFi：2 个 8 s 窗口的 `iwpriv rai0 stat` 增量（用于区分累计值与实时值）
- conntrack：4 次不同时刻采样

**已知局限**：
1. **本固件不暴露 PPE 统计**（debugfs 无 ppe 节点、dmesg `stats 0x0`）→ 硬件加速结论是结构推断，非直接计数。
2. **未测速** → 所有吞吐数字均为估算。
3. 采样时处于**低负载**状态（load 0.2），峰值表现需在真实大流量下复测。
4. `mt7916` 驱动的 `Current BW Tx count` / `Other BW Tx count` 计数语义未在驱动源码中确认，其"1.3% 在当前带宽"的解读存疑，已在正文标注。
5. 5G CRC 误码的两个候选成因（同频冲突 / 弱 STA）**未做区分实验**（需改信道后复测，本次为只读审计故未做）。
6. 部分 `nft list chain` 查询返回空（busybox nft 对部分 chain 名的解析限制），已用 `nft -a list table` 取到完整规则与计数器。
