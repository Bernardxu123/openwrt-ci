### B. packet steering 修正（`packet_steering=2`）+ WiFi NAPI 绑核

**问题根因**：OpenWrt 的 `/usr/libexec/network/packet-steering.uc`（注意是 **ucode**，不是 `.sh`）按 netdev 名匹配 NAPI 线程，airoha 的以太网 NAPI 线程叫 **`napi/qdma_eth-0`**，而对应 netdev 叫 `pon0`（**名字对不上**）→ 脚本判定「无 NAPI 可绑」，把 64 条 RX 队列的 RPS 全部指向 CPU0。

**修复**：

```sh
uci set network.globals.packet_steering='2'   # 2 = RPS，不动 RFS
uci commit network
/etc/init.d/packet_steering reload
```

`packet_steering=2` 的语义：**保留 RPS（由内核在 CPU 间分发软中断），不启用 RFS（不做每核队列）**。实测 `NET_RX` 软中断从 CPU0 迁移到 CPU1。

**副作用与补丁**：开了 steering 后，WiFi 的 6 个 `napi/phy0-0`（2.4G）线程被从 CPU3 挪到了 **CPU0**（`taskset` 实测 mask `8`=CPU3 vs `1`=CPU0）。这会跟以太网抢核，故新增一个常驻服务把 WiFi NAPI 钉回 CPU3：

`/etc/init.d/wifi-napi-affinity`（已 `enable`，`START=26`）：

```sh
#!/bin/sh /etc/rc.common
START=26
USE_PROCD=1

pin_loop() {
	for i in 1 2 3 4 5; do
		for p in $(ps w | awk '/napi\/phy[0-9]+-/ {print $1}'); do
			taskset -p -c 3 "$p" >/dev/null 2>&1
		done
		sleep 1
	done
}

start_service() { pin_loop & }
reload_service() { pin_loop & }

service_triggers() {
	procd_add_reload_trigger "network"
	procd_add_reload_trigger "firewall"
}
```

> 为什么是「循环 5 秒 × 1 秒间隔」而不是一次性：mt76 的 NAPI 线程会随 WiFi 重新加载而**重建**，PID 变化、亲和性复位。所以要在 network/firewall 触发的窗口内反复钉。实测 `/etc/init.d/packet_steering reload` 后约 3 秒内恢复到 CPU3。
> **副作用**：WiFi 收包固定压 CPU3 → 满载时 CPU3 会成为瓶颈（见 §5 实测数据）。若改成 CPU2/CPU1 分摊需另行实测。

### C. `/sbin/tempinfo`（温度聚合）

QWRT 的 `sbin/tempinfo` 读 CPU thermal_zone + WiFi hwmon + PON 光模块温度，喂 LuCI 概览页。ponwrt 侧照抄一份：

```sh
#!/bin/sh
cpu=""; pon=""; wifi=""
[ -r /sys/class/thermal/thermal_zone0/temp ] && cpu="$(awk '{printf "%.1f°C", $1/1000}' /sys/class/thermal/thermal_zone0/temp)"
for f in /sys/class/ieee80211/phy*/hwmon*/temp1_input; do
  [ -r "$f" ] || continue
  wifi="$wifi$(awk '{printf "%.1f°C ", $1/1000}' "$f")"
done
if [ -x /usr/sbin/ponctl ]; then
  t="$(/usr/sbin/ponctl --device pon0 status --json 2>/dev/null | jsonfilter -e '@.frontend.temperature_celsius' 2>/dev/null)"
  [ -n "$t" ] && pon="$(awk -v v="$t" 'BEGIN{printf "%.1f°C", v}')"
fi
out=""
[ -n "$cpu" ] && out="CPU: $cpu"
[ -n "$pon" ] && out="${out:+$out, }PON: $pon"
[ -n "$wifi" ] && out="${out:+$out, }WiFi: ${wifi% }}"
[ -n "$out" ] || out="No temperature info"
printf '%s' "$out"
```

> 注意 `jsonfilter -e '@.frontend.temperature_celsius'` 是 **qca-nss-ecm 无关的 ponctl 字段路径**（QWRT 仓库 `luci-app-pon-status` 也用同一路径），ponwrt 的 `ponctl` 需实测是否同结构 —— **本机尚未验证 PON 温度字段是否返回**（CPU / WiFi 两项已验证）。

## 5. 为什么判定「硬件卸载不会绕过 tproxy」（证据链）

这是本次最关键的一条，因为它直接推翻了本仓库 `99-hg5585f-setup` §6 的既有假设。

1. **机制上**：tproxy 在 **prerouting** 就把包截下并本地投递，被代理的 flow **永远进不了 forward 方向的 flowtable**，因此 PPE 根本看不到它 —— 硬件卸载**只作用于直连/未代理流量**。
2. **实测上**（开 `hw=1` 前后对比）：
   - 代理出口 IP 不变（`155.254.108.53`）→ 代理流没被甩给 PPE 直连出去；
   - YouTube `generate_204` 仍 204；
   - 直连大文件下载正常；
   - `npu_attached` 0→1 说明硬件路径**确实被激活**（不是「开了没生效」）；
   - ONT 无线在线客户端数（2.4G 10 / 5G 7，`iwinfo assoclist` 统计）开关前后无变化 → 没有把在线设备踢掉；
3. **反向风险**：仓库脚本担心的现象（部分站点直连、规则不生效）**在本机未复现**。

> 保守起见仍建议保留一条人工回退路径（见 §7 命令）。

```sh
cat /proc/net/softnet_stat                               # 每行一 CPU：第 1 列 dropped、第 3 列 time_squeeze
cat /proc/softirqs | grep NET_RX                          # NET_RX 各 CPU 分布

# —— 绑核 / steering ——
uci show network.globals | grep steering
ps w | awk '/napi\/phy[0-9]+-/ {print $1}' | xargs -r -n1 taskset -p
/etc/init.d/packet_steering reload

# —— 温度 ——
/sbin/tempinfo

# —— 回退硬件卸载（最保守）——
uci set firewall.@defaults[0].flow_offloading_hw='0'
/etc/init.d/firewall reload
# 完全回到出厂状态：
uci revert firewall && /etc/init.d/firewall reload
```

## 8. 负面清单（本轮踩过的坑，别再踩）

1. **`nft list flowtable inet fw4 ft` 才是正确语法**；写成 `nft list inet fw4 ft` 会报语法错。
2. **别用 `sed -n '/flowtable ft {/,/}/p'` 截 flowtable 输出** —— `devices = { ... };` 里的 `}` 会把命令提前截断，**会误判 `flags offload` 缺失**。用 `grep -A7`。
3. **`ssh_script.py` 在本机不可用**：dropbear 无 SFTP 子系统 → `EOF during negotiation`。传脚本用 base64 管道：`echo '<b64>' | base64 -d > /tmp/x.sh && sh /tmp/x.sh`。
4. **`packet_steering.uc` 是 ucode 不是 shell**，且**匹配的是 netdev 名**；airoha 的 NAPI 线程叫 `napi/qdma_eth-0` 而 netdev 叫 `pon0` → 官方脚本对 airoha 基本无效，只能用 `=2`（纯 RPS）绕开。
5. **`packet_steering=2` 会把 WiFi NAPI 挪到 CPU0**（实测），必须补绑核服务，否则 WiFi 抢以太网核。
6. **我曾误判「板载 WiFi 是关的」** —— 起因是只看了仓库默认值和 `/sys/class/ieee80211` 是否存在，没查 `uci show wireless`。实测 `radio0/1 disabled=0`（2026-10-20 当晚在线客户端 2.4G 10 / 5G 7）。**结论：凡涉及「某功能开没开」，一律用 `uci show` / 运行时状态核对，不要用仓库默认值推。**
   - 附带坑：`iwinfo assoclist` 输出的 MAC 是**大写**，统计客户端数要用 `grep -icE '^([0-9a-f]{2}:){5}[0-9a-f]{2}'`；漏了 `-i` 会数出 0。
7. **拟合参数别照抄 QWRT**：QWRT `packet_steering` 生效的前提是它的线程名匹配；我方要另测。
8. **`run(dry:true)` 之类的「只校验」语义**（Passwall/dae 通用坑）：**永远不要用 dry-run 当校验器**，会真 reload 并把服务打没（见 AGENTS.md §六.8）。
