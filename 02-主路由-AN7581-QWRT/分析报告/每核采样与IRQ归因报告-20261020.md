# 每核性能采样与 IRQ 亲和性分析报告（ponwrt / HG5585F-CU）

> **日期**：2026-10-20 19:51–19:55
> **目标机**：烽火 HG5585F-CU（AN7581，4×Cortex-A53 @ 500–1200MHz），PonWrt SNAPSHOT r0-e585ae8（kernel 6.18.55），主路由 `192.168.31.1`
> **采样工具**：本仓库 `tools/cpu_percore_sample.sh` + `tools/cpu_percore_analyze.py`
> **原始数据**：`backups/cpusample-20261020/`（procstat.raw / net.raw / interrupts.raw / interrupts.end / meta.txt / analysis.txt）
> **本报告目的**：把采样结论写清楚，交给别人继续实施优化。

---

## 0. 一句话结论

采样窗口里**确实发生了一次完整的手机 WiFi 测速**（上传 182Mbps → 下载 901Mbps → 上传 53Mbps），
所以数据有效。在此期间**CPU0 被打到 94.3% busy，其中 irq+softirq 占 ~46%**。
根因不是 `packet_steering=2` 造成的，恰恰相反——**`packet_steering=2` 是让 CPU0 缓解的那一步**；
真正的瓶颈是 **所有硬件中断（mt7915e WiFi + airoha_eth 以太网）全部落在 CPU0**，GICv3 的
`effective_affinity` 被硬钉在 CPU0，`smp_affinity_list` 写了也不生效（`Result not representable` / `Operation not permitted`）。

**下一步唯一值得做的事：把 mt7915e 的 MSI 中断（irq 53）从 CPU0 迁走。** 这是可做的（见 §5），收益直接命中 CPU0。

## 1. 采样窗口内的真实流量（不是空闲）

用 `/proc/stat` + 各网卡 `rx_bytes/tx_bytes` 逐秒对齐，窗口内出现三段明显业务：

| 时间窗 (相对采样起点) | 事件 | 峰值 |
|---|---|---|
| t ≈ 11–16 s | **上传**（手机 → PON） | `pppoe-wan tx` 182 Mbps，`pon0 tx` 185 Mbps |
| t ≈ 15–26 s | **下载**（PON → 手机 5G） | `pon0 rx` 901.8 Mbps，`phy1-ap0 tx` 858.4 Mbps，`br-lan tx` 813.6 Mbps |
| t ≈ 27–42 s | **二次上传**（小包） | `pppoe-wan tx` 53.8 Mbps，`phy1-ap0 rx` 53.6 Mbps |
| t > 50 s | 空闲 | 全网 < 0.1 Mbps |

关键点：
- 流量走的是 **5G（`phy1-ap0`，`bernard_5G`）**，不是 2.4G。`phy0-ap0` 全窗口峰值仅 9.1 Mbps。
- `pon0 rx` 峰值 901.8 Mbps 与 `phy1-ap0 tx` 峰值 858.4 Mbps 高度吻合 → **PON 下行 900M 直接灌到 5G 无线客户端**，
  是一条完整的「有线进、无线出」路径。
- `pppoe-wan rx` 全程 < 0.3 Mbps（下行走 `pon0.995`→`pppoe-wan`，被 `pppoe-wan rx` 计到；`pppoe-wan tx` 才有量）。

读法：`irq` 列 = `/proc/stat` 第 6 项（`irq`）+ 第 7 项（`softirq`）合并。

### 2.3 三个结构性观察

**(a) CPU0 的 busy 几乎全是内核态，不是用户态**
峰值时 `usr ≈ 0%`，`sys ≈ 45–53%`，`irq+softirq ≈ 40–46%`。用户态几乎为 0 ⇒
**这不是 xray / passwall 吃 CPU，是中断 + 内核网络栈吃 CPU。**
（旁证：`/tmp/etc/passwall/bin/xray` 峰值期 utime 增量很小；`top` 快照里 xray `%CPU` 也是 0%。）

**(b) CPU3 在 19–24 s 出现第二个尖峰（83.7%，其中 sys 79.4%）**
这是 **WiFi 侧的处理**。`/etc/init.d/wifi-napi-affinity` 把 2.4G 的 6 个 `napi/phy0-0` 线程钉在 CPU3；
5G 的 `napi/phy1-0` 线程**没有对应条目**（`ps` 只有 `napi/phy0-0` 和 `napi/qdma_eth-0`），
所以 5G 的软中断/NAPI 落在哪由内核默认决定，实测表现为 CPU3 的 sys 暴涨。

**(c) CPU1 / CPU2 全程基本闲着（峰值 60% / 60%，avg 不到 11%）**
四核里有两核几乎没用上，**负载分布是失衡的**。

## 3. IRQ 归因（本报告的核心证据）

采样窗口两端 `/proc/interrupts` 差分：

```
   11 GICv3 30 Level arch_timer              cpu0=18213 cpu1=16241 cpu2=16791 cpu3=19781
   19 INTx 0 Edge -INTx mt7915e-hif          cpu0=45216 cpu1=0     cpu2=0     cpu3=0      ← WiFi
   23 GICv3 69 Level airoha_eth.0             cpu0=12510 cpu1=0     cpu2=0     cpu3=0      ← 以太网
   27 GICv3 70 Level airoha_eth.4             cpu0=446697 cpu1=0   cpu2=0     cpu3=0      ← 以太网(主)
   53 MTK3-PCI-MSI-0001:01:00.0 mt7915e       cpu0=40991 cpu1=0     cpu2=0     cpu3=0      ← WiFi MSI
   54 GICv3 74 Level 1fb64000.ethernet        cpu0=78    cpu1=0     cpu2=0     cpu3=0
 IPI0 Rescheduling interrupts                 cpu0=6355 cpu1=6549 cpu2=6592 cpu3=6045
 IPI1 Function call interrupts                cpu0=42446 cpu1=232208 cpu2=288135 cpu3=174813   ← 软中断派发
 IPI5 IRQ work interrupts                     cpu0=1552 cpu1=1662 cpu2=2138 cpu3=2368
```

### 3.1 硬件中断 100% 集中在 CPU0

- **mt7915e（WiFi 芯片）**：irq 19（INTx）+ irq 53（PCIe MSI），共 **86,207 次，全部在 CPU0**，其它三核 0。
- **airoha_eth（以太网/PON）**：irq 23 + irq 27，共 **459,207 次，全部在 CPU0**。
- 合计 **~545,000 次硬件中断，100% 落在 CPU0**。

### 3.2 软中断（NET_RX）已经散开了 —— 这是 `packet_steering=2` 的功劳

```
/proc/softirqs  NET_RX:  CPU0=80273160  CPU1=13042543  CPU2=2093308  CPU3=893422
```

累计值 CPU0 仍是 80M（历史包袱，改动前的旧账），但 **IPI1 Function call interrupts**
（内核把软中断派发到别的 CPU 的信号）在 CPU1/2/3 上分别是 232K/288K/175K，
证明 **RPS 正在把 NET_RX 往 CPU1/CPU2/CPU3 分发**——这与用户自己观测到的
「同一轮 4 并发下载：CPU0 +124 / CPU1 +8,496 / CPU2 +30 / CPU3 +8」完全吻合。

**所以：`packet_steering=2` 确实生效了，而且是往对的方向走。CPU0 压力不是它造成的。**

### 3.3 为什么 CPU0 还是被打爆：GICv3 的 effective affinity 钉死在 CPU0

```
irq 19 (mt7915e-hif):  smp_affinity_list=0-3   effective_affinity_list=<空>   eff_hex=0
irq 23 (airoha_eth.0): smp_affinity_list=0-3   effective_affinity_list=0      eff_hex=1
irq 27 (airoha_eth.4): smp_affinity_list=0-3   effective_affinity_list=0      eff_hex=1
irq 53 (mt7915e MSI):  smp_affinity_list=0-3   effective_affinity_list=<空>   eff_hex=0
irq 54 (ethernet):     smp_affinity_list=0-3   effective_affinity_list=0      eff_hex=1
```

`smp_affinity_list` 显示 `0-3`（四核全开），但 **`effective_affinity_list` 实际是 `0`**（只有 CPU0）。
即：**内核记录了"想放四核"，但 GICv3 硬件层只把中断投递给 CPU0。**

实测写入行为（`/proc/irq/N/smp_affinity_list`）：

| irq | 目标 | 结果 |
|---|---|---|
| 27 (airoha_eth.4) | `2` | ✅ **成功**，`effective_affinity_list` 变 `[2]`，中断计数随即出现在 CPU2（6 秒内 +10,612） |
| 27 (airoha_eth.4) | `0-3` / `0` | ✅ 成功，能改回去（**已恢复原状**） |
| 53 (mt7915e MSI) | `4` (CPU2) | ❌ `Operation not permitted`（PCIe MSI 由 PCIe 控制器/MSI 控制器管，内核改不动） |
| 23 (airoha_eth.0) | `8` (CPU3) | ❌ `Result not representable`（GICv3 该 SPI 的 target 寄存器受限） |
| 54 (ethernet) | — | 同上类 |

> ⚠️ 写入 `f`（十六进制）会 `Invalid argument`，**必须写列表格式** `0-3` 或十进制 `2`。
> ⚠️ 本次实验已把 irq 27 恢复成 `smp_affinity_list=0-3` / `effective_affinity_list=0`，与改动前一致。

## 4. 归因结论：到底是不是"改动导致的"

| 现象 | 是不是本次改动（packet_steering=2 / wifi-napi-affinity / hw offload）导致 | 真正原因 |
|---|---|---|
| CPU0 峰值 94.3% | **不是**。`packet_steering=2` 恰恰把软中断从 CPU0 分流走了（IPI1 证据） | **所有硬件中断被 GICv3 钉在 CPU0**：mt7915e 的 irq19+irq53（86K 次）、airoha_eth 的 irq23+irq27（459K 次）全在 CPU0 |
| CPU0 的 sys 高达 53% | 不是 | 内核网络栈在 CPU0 上跑全部硬中断处理 + 一部分 NET_RX |
| CPU3 峰值 83.7%（sys 79.4%） | **部分是**。`wifi-napi-affinity` 只钉了 2.4G 的 `napi/phy0-0`（6 个）到 CPU3，**5G 的 `napi/phy1-0` 没有被钉**，负载撞在 CPU3 | 5G NAPI 未被显式绑核；且 WiFi 侧中断本身也全在 CPU0 |
| CPU1/CPU2 闲置 | 是次要因素（steering 把以太网 NAPI 偏向了 CPU0/CPU1） | 硬中断不分核 + NAPI 绑定不均 |
| 硬件 offload 未绕过 tproxy | **不是问题，实测确认绕过不了**（代理出口 IP 仍是 `155.254.108.53`，YouTube 204，直连 100MB 正常） | — |
| 硬件 offload 对本次 WiFi 大流量**没起作用** | — | PPE 有 156 条表项，但 5G 客户端流量必然经 CPU（mt76 无硬件卸载能力），PPE 帮不上 |

### 4.1 一句话回答提问

**「是不是改动导致的？」→ 不是。**
改动（`packet_steering=2` + `wifi-napi-affinity`）方向是对的，**软件层面能做的都做了**。
CPU0 之所以还是 94%，是因为**中断的硬件亲和性被 GICv3 钉死在 CPU0，这不在 `packet_steering` 的管辖范围内**。
继续在 `packet_steering` / `wifi-napi-affinity` 上加码，边际收益已经很薄；
**要动的是 IRQ 亲和性这一层。**

## 5. 下一步实施建议（按性价比排序，交接给实施者）

### P0 — 把 mt7915e 的 WiFi 中断从 CPU0 迁走（最大收益）

irq 53 是 PCIe MSI，内核 `/proc/irq` 写不进去，需要走 **PCIe MSI 控制器 / `pci=nomsi` / 中断亲和性 hint**：

```sh
# 思路 A：先确认 MSI 的 affinity 是不是真的写不进去（有些内核允许写 msix 而非 msi）
cat /proc/irq/53/smp_affinity_list          # 期望 0-3
echo 2 > /proc/irq/53/smp_affinity_list     # 前面实测 EPERM
echo 4 > /proc/irq/53/smp_affinity_list     # 也 EPERM

# 思路 B：内核参数给 mt7915e 的 irq 亲和性 hint（驱动支持 irq affinity 的前提是走 MSI-X）
#   在 /etc/config/boot 或 cmdline 加：
#   pci=nomsi                      # 强制 INTx（牺牲吞吐换亲和性可写，副作用大）
#   或 mt7915e.core.pci_msi_avoid_irq=

# 思路 C（推荐先做）：退一步，把 WiFi NAPI 线程分散到 CPU1/CPU2，
#   让 CPU3 不再是唯一落点。见 P1。
```

### P1 — 补齐 5G 的 NAPI 绑核（`wifi-napi-affinity` 的直接补丁）

现状 `wifi-napi-affinity` 只匹配 `napi/phy[0-9]+-`，实测只抓到 6 个 `napi/phy0-0`（2.4G），
**5G 的线程没抓到**（`ps` 全量：`napi/phy0-0` × 6、`napi/qdma_eth-0` × 68，没有 `napi/phy1-0`）。
需要：
1. 确认 5G 的 NAPI 线程到底叫什么（可能在 `/proc/*/comm` 里显示为 `mt7915e` 或其它名字）——
   用 `ps w | grep -i napi` + `cat /proc/<pid>/comm` 逐个核对；
2. 把 WiFi NAPI **按轮转摊到 CPU1/CPU2/CPU3**（而不是全塞 CPU3），
   例如把 2.4G→CPU3、5G→CPU1，把 CPU2 空出来；
3. 避免与 `packet_steering` 的 `assign_dev_queues_cpu` 打架（它每 5s 会重钉一次，
   当前脚本用 `taskset -p -c 3` 覆盖，需要确认谁最后生效）。

### P2 — 让 airoha_eth 的两个大 IRQ 分散（irq 27 已被证明可写）

irq 27（airoha_eth.4，446K 次，量最大）**实测可改**：

```sh
echo 2 > /proc/irq/27/smp_affinity_list   # → CPU2，实测中断随即迁移
# 验证：cat /proc/irq/27/effective_affinity_list 应为 [2]
#       6 秒后再看 /proc/interrupts 该行的 cpu2 列应有增量
# 回滚：echo 0-3 > /proc/irq/27/smp_affinity_list
```

⚠️ 必须写成列表或十进制，**写 `f` 会 Invalid argument**。
建议做成开机脚本（`/etc/init.d/` 或 `/etc/rc.local`），但**先只改 irq 27（可回滚），
irq 23 / irq 54 写不进去，不要浪费时间**。

### P3 — 硬件 offload 决策（用户侧待拍板）

- 现状：已生效但**未 `uci commit`**，`uci changes` 显示 `firewall.cfg01e63d.flow_offloading_hw='1'`。
- 回滚：`uci revert firewall && /etc/init.d/firewall reload`
- 固化：`uci commit firewall`
- ⚠️ 仓库 `99-hg5585f-setup` 里有「检测到 Passwall 就强制 FLOW_HW=0」的逻辑，
  **下次刷机/重跑脚本会被打回**——要固化必须同时改仓库那段。
- **但注意**：本次采样证明，硬件 offload 对「WiFi 客户端大流量」**没有帮助**
  （5G 路径必然经 CPU），所以固化的收益主要体现在**有线客户端**场景，别把它当 WiFi 提速手段。

## 6. 复现方法（给实施者）

```powershell
# 一键上传并后台起采样（dropbear 无 SFTP，走 stdin）
python tools\upload_run_bg.py tools\cpu_percore_sample.sh /tmp/cpu_percore_sample.sh 125
```

辅助工具（本轮新增，均在 `tools/`）：
| 文件 | 用途 |
|---|---|
| `cpu_percore_sample.sh` | 路由器端采样器：每核 `/proc/stat` + 各网卡字节 + IRQ 基线/尾帧 |
| `cpu_percore_analyze.py` | 本地分析：逐秒每核 busy%、网卡 Mbps 时间线、IRQ 差分表 |
| `fetch_cpusample.py` | 从路由器拉 `/tmp/cpusample/*` 存档 |
| `upload_run.py` / `upload_run_bg.py` | 通过 stdin 传脚本（前台 / 后台）——**dropbear 无 SFTP**，`ssh_run.py` 会被 PowerShell 的 `$(...)` 吃掉，必须走脚本上传 |
| `probe_irq_affinity.sh` / `probe_irq_affinity2.sh` | IRQ→CPU 绑定、NAPI 线程、RPS/XPS、softnet_stat 全景 |

## 7. 待补充核实（下一轮必做）

1. **5G 的 NAPI 线程真实名字**（`/proc/<pid>/comm` 全量扫描），才能补 P1 的绑核。
2. **`mt7915e` 是否支持 MSI-X**（决定 irq 53 亲和性到底有没有救）：
   `ls /sys/bus/pci/devices/*/msi_irqs/`、`cat /proc/irq/53/*`。
3. **irq 53 不可写的确切原因**：是 PCIe MSI（`MSI_IRQ`）还是 MSI-X？前者内核可写、
   后者要看 `msix_irqs`——目前 `irq 53` 名称含 `MTK3-PCI-MSI`（非 MSI-X），
   理论上应可写却 EPERM，**需要看内核 `mt7915e`/`mt76` 的 `request_irq` flags**。
4. **硬件 offload 对有线客户端的实际收益**（当前 156 条 PPE 表项 / `npu_attached=1`，
   但没测出有线侧吞吐增益）。
